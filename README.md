# AETHER — SDF 光線行進

一個完全跑在 GPU 上的場景。**零依賴、零建置、零打包器**：沒有 npm、沒有框架、沒有函式庫，
`index.html` 開起來就是全部。所有東西都是 `<canvas>`、原生 ES modules，與手寫 GLSL。

**距離場裡沒有任何一個頂點、沒有任何一個三角形。** 一道 fragment shader 沿著射線走進由距離函數
定義的隱式曲面：一團互相以 smooth-min 焊接的公轉球體，加上一個以自己的節奏翻滾的環。
陰影來自朝光源再走一次，環境遮蔽來自在命中點周圍取樣距離場，反射來自沿鏡射方向再走一次，
抗鋸齒來自每幀抖動取樣點再讓時間累積把它收斂掉。

**點擊星體或星環，被碰到的那一點會盪出漣漪** —— 表面凹出一個火山口，
一圈熾熱的環沿著表面擴散出去。把「質量消散」拉大，那一擊會把星環啃出一個缺口、
甚至把球體吃穿；能量排空之後兩者都長回來。

場景裡唯一由三角形構成的東西是**那隻貓**，用 `WASD` 驅動牠在地面上走動。牠不走同一條管線，
兩者在「深度」相接；星團會在牠身上投影，牠也會在地板上投影 ——
見〈[一隻光柵化的貓](#一隻光柵化的貓)〉。

## 點擊漣漪

點擊需要一個 shader 給不出來的答案：**游標底下是什麼？** 所以射線在 CPU 上再走一次，
對著同一組基本形體。也因此球體座標改由 JS 計算後上傳，而不是在 shader 裡從 `uTime` 推導 ——
一個現在有兩個讀者的場景，需要單一真相來源，兩份同樣的公式正是會悄悄走偏的那種東西。

CPU 的那次行進刻意**不含**表面擾動與漣漪：它們最多把表面推開兩公分，遠低於一次點擊需要的
精度，而納入它們會讓每次點擊都付一次噪聲函數的代價。法線用中央差分取六個樣本 ——
一次點擊跑一次，不是一個像素跑一次。

撞擊由三件事構成：

**凹陷與波。** 加在**距離場本身**上的一項。沒有網格可以推，所以波不是被畫上去的，
**波就是表面**。這一項的梯度會隨振幅與波數線性上升，所以行進步長是**從它們推導**的，
不是猜一個常數：把深度調高，追蹤器會變慢，而不是穿過表面。
（預設值算出來剛好是 0.88 —— 也就是這個機制取代掉的那個寫死的數字。）

**質量消散。** 波只能把表面推開一點點，再深就不再是距離場了。要真的少掉材料，
最直覺的做法是布林減去一顆球 —— 精確、便宜，但它留下一道**車床切出來的圓形邊緣**，
那不是任何能量真的會造成的斷面。

所以這裡用的是**加法**：能量高的地方把表面往內推，邊緣是平滑收細而不是被切開。
消散量超過當地厚度的地方，表面就直接不存在了 —— 星環只有 0.075 厚，
所以那裡會裂開一個缺口。

**癒合時收縮的是受損區域的半徑，不是深度。** 讓深度均勻淡出是直覺的做法，而且是錯的：
任何小到整個落在受損範圍裡的東西，會先縮小、再從自己的正中央長回來。改成收縮邊界之後，
最外圈的材料先回來、中心是最後閉合的那一點 —— 那才是一個洞真正癒合的樣子。

**波在受損區內被靜音。** 行進中的正弦有負相位，而負相位會把表面往**外**推 ——
不處理的話，缺口會在中央長出一小塊材料，跟著波前一路帶到邊緣。
已經消散掉的東西，沒有介質可以承載波。

加法還有一個好處：它的梯度是「振幅除以邊緣寬度」而不是「振幅乘以波數」，
而那個邊緣寬度是固定的，所以它直接吃前面那套「步長從場扭曲推導」的機制，
不需要任何特例，也不會因為撞擊處在生命週期的哪個階段而改變成本。

這一項放在**形狀層**而不是完整層：缺口對陰影與遮蔽射線也必須是缺口，
否則你會看到光拒絕穿過一個明明看得穿的東西。

**衝擊環。** 單靠幾何位移，在一個平滑的奶油色曲面上就是「技術上正確、但幾乎看不見」。
所以波前另外帶一圈**發光**——那是 emission 不是幾何，不花任何距離場穩定性的代價，
而且一眼就讀得到。

漣漪的圓心每幀從它撞上的東西重新算，不是撞擊當下烙在世界座標上：球體在公轉**而且會脈動**，
所以存的是一個**方向**、每幀重新貼回表面；星環則存環座標系裡的點再轉回來。
（驗收工具會檢查這件事：漣漪中心在半秒內確實被宿主帶著移動了。）

**點擊與拖曳**靠按下到放開之間指標移動了多遠來區分 —— 而且是在**事件**上判定，
不是在算繪迴圈裡取樣：25 fps 的場景上，一次快速點擊可能整個發生在兩幀之間。

## 值得一看的幾個決定

**Uniform 反射。** GPU 在連結程式時就已經知道每個 uniform 的名字、型別與位置，所以要求作者
在 JS 裡再抄一遍純粹是重複。[`core/program.js`](src/core/program.js) 讀一次反射資料，
之後 `prog.use({ ... })` 依型別自動分派到正確的 `gl.uniform*`，並把材質綁到自動指派的
texture unit。整個專案沒有一行 `getUniformLocation`。

**沒有建置步驟，所以 GLSL 就是 JS 模組。** 沒有 `#include`，共用著色器碼就放在
[`shaders/common.js`](src/shaders/common.js) 的字串常數裡用 `${}` 組合。這不是妥協 ——
它意味著著色器由瀏覽器自己的模組圖管理，沒有前處理器需要除錯。代價是：GLSL 註解裡不能有反引號，
不然樣板字串會提前結束（這件事花了一次 boot failure 才學會）。

**一個超大三角形，不是兩個。** 覆蓋全螢幕用 `(-1,-1) (3,-1) (-1,3)`：沒有對角接縫、少一個頂點，
而且 GPU 不會在斜邊重複光柵化同一個 pixel。

**Ping-pong 是型別的一部分。** `DoubleTarget` 把 `.read` / `.write` / `.swap()` 包在一個物件裡，
消滅了最常見的 bug：忘記自己在哪一半。時間累積就是靠它 —— 對著同時是當前 colour attachment
的材質取樣是未定義行為，而它產生的瑕疵看起來夠合理，合理到可以浪費你一個晚上。

**免費的抗鋸齒。** 每個 pixel 每幀把射線方向抖動不到一個 pixel，再讓時間累積把這些樣本平均掉。
鏡頭移動時混合係數自動調低，否則抖動會變成拖影。

**參數即 URL。** `#/march?balls=9&blend=0.55` 是你眼前畫面的完整描述。拖曳 slider 時用
`replaceState` 寫回位址列 —— 值得分享的狀態就是能寄給別人的狀態。驗收工具也靠這個擺場景。

**自訂元素包住原生控制項。** 每個 widget 底下都是真正的 `<input type=range>` /
`<button role=switch>`，只有像素是我們的。鍵盤操作、螢幕閱讀器語意、IME 行為全部來自平台。

**時間分兩種。** `clock.dt` 是模擬時間（可暫停、可縮放），`clock.wallDt` 是真實時間（永不為 0）。
暫停場景不會讓 UI 動畫卡住；一個異常長的幀（切回分頁、著色器重編譯）永遠不會被交給
積分器 —— dt 上限鎖在 1/20 秒。

## 一隻光柵化的貓

貓是一份程序化模型：~40 顆球體／管狀體，經過二次塑型、頂點染色、反殼描邊，
原始碼在 [tools/cat-model.js](tools/cat-model.js)。它**不 import three，THREE 由呼叫端傳入**，
所以能在 Node 裡跑 —— 我們跑它一次，把 three 丟掉，留下頂點。

模型與它需要的 three 都**放在本專案的 `tools/` 裡**，烘焙不讀取這個 repo 以外的任何東西。
`tools/` 是冷路徑：不會被 serve、不會被打包、app 不會 import 它 —— app 本身依然零依賴。
保留三個花色（橘白／虎斑／三花），其餘沒有帶進來。

### 兩條管線在哪裡相接

不是在幾何上，是在**深度**上。這個場景本來就已經把深度公開了：march pass 把射線走過的距離
寫進 colour target 的 alpha，好讓撞擊閃光能躲在幾何後面（`outColor.a = mat > 0.5 ? t : 1e4`）。

貓寫同一個量 —— `length(world - camera)`，同樣的單位 —— 進自己 target 的 alpha。
於是合成就只是每個 pixel 一次比較，寫在時間累積那一遍裡：

```glsl
vec4 scene = texture(uSrc, vUv);
vec4 mesh  = texture(uMesh, vUv);
if (mesh.a < scene.a) col = mesh.rgb;
```

（後來草地也走這條路，所以那張 target 叫 `meshRT` 而不是 `catRT`：貓和草**共用同一個
depth buffer**，這就是為什麼貓是站「在草裡」而不是站在草的圖片上。）

畫布上**依然沒有 depth buffer**（`depth: false` 沒有動過）。貓自己的 target 掛了一個私有的
depth renderbuffer，那只是為了讓牠自己的三角形彼此排序。march 完全不知道貓存在。

投影矩陣不是另外建的，是從 march 用的同一組 `uRight/uUp/uFwd/uFocal` 反推出來的 ——
沒有第二份相機資料可以走偏。

### 兩種操作方式（按 `Y` 切換）

| | 轉向 | WASD 的座標系 |
|---|---|---|
| **依鏡頭方向**（預設） | WASD 指哪就轉去哪 | **畫面**：`W` 遠離你、`S` 朝向你 |
| **滑鼠轉向** | 滑鼠滑動，不用按鍵 | **身體**：`W`／`S` 沿鼻尖，`A`／`D` 左右平移 |

模式名字說的就是「WASD 是用哪個座標系表達的」，差別全部在這裡。

預設模式下貓**永遠只往前走** —— 沒有倒退、沒有側移，因為動物是轉過身再走的。
按 `S`，牠會轉過來朝你走過來。速度會依「身體已經多接近目標方向」縮放（有下限）：
沒有這個縮放，貓每次掉頭都在甩尾漂移；沒有下限，牠每個轉角都會停死。

只有滑鼠轉向模式能讓貓往「牠沒有面向的方向」移動。

**一個必須成對處理的陷阱**：WASD 既然是用鏡頭的座標系表達，跟隨鏡頭就**不能**追著貓的朝向轉。
否則按住 `S`：貓轉過來面向你 → 鏡頭繞到牠身後 → 「朝向你」現在指向別的地方 → 牠再轉一次 ——
原地無限打轉。所以依鏡頭方向模式下，跟隨鏡頭**只追位置，朝向留給使用者拖曳**；
只有滑鼠轉向模式才把鏡頭釘在貓身後。

**指標鎖定**是讓滑鼠轉向真的可用的關鍵：沒有它，游標會撞到螢幕邊緣，轉一半就轉不下去了。
鎖定在按下 `Y` 的那一刻請求 —— 按鍵正好是瀏覽器要求的 user gesture。

但它**不是必要的**。如果鎖定被拒絕（嵌入式或自動化的文件可能根本不被允許），或使用者按 `Esc`
放掉了，這個模式仍然能用 app 本來就在累積的 pointer delta 運作 —— 只是會用完桌面空間。
點畫布可以重新鎖定。降級成堪用，比整個模式拒絕運作好。

被拒絕是常態而非例外，所以那個 promise rejection 是被吞掉的 —— 放著不管會浮出成
unhandled rejection，看起來像故障，但它不是。

兩個順帶的後果：
- 滑鼠已經有工作了，所以**滑鼠轉向模式下拖曳不再繞行鏡頭** —— 否則兩者會搶同一個位移。
- 指標被鎖定時沒有游標位置可以瞄準，所以**點擊改成打畫面正中央**。反正十字準星本來就是這樣，
  漣漪在滑鼠轉向模式下照常能打。

跟隨鏡頭在這個模式下是**直接釘在 `catYaw + π`**、不做緩動：滑鼠就是鏡頭，任何延遲都會讀成畫面卡住。

### 眼部雷射：對星體的動能

在**跟隨貓的鏡頭**下按左鍵，從貓的雙眼射出兩道紅色雷射，一路打穿星體與星環。
鏡頭鎖定在星團上時不會開火 —— 那個模式是在**看**它，不是在**當**牠，點擊仍然是打在表面上。

瞄準方式看**指標有沒有被鎖定**：

| | 瞄準 | 扳機 |
|---|---|---|
| 已鎖定（滑鼠轉向） | 準心，也就是鏡頭前方 | **按住連發**（0.13 秒一發） |
| 未鎖定 | 游標指到的那個點 | 一次點擊一發，**點空不發射** |

未鎖定時貓會**先轉身面向目標再射**，光束是「貓眼 → 目標點」的連線，不是鏡頭的方向 ——
除非你正好站在牠正後方，否則那是兩個看得出差別的方向。

### 頭先轉，身體才跟

看東西的是頭，不是身體。所以瞄準時**脖子先轉**，肩膀只補它轉不完的部分 ——
再加一點點，因為完全不動肩膀的貓會變成貓頭鷹。脖子的範圍是 ±0.9 弧度（約 52°），
超出的部分才交給身體；範圍內身體也只跟轉 25%。

頭同時會**依光束的仰角俯仰**。頭骨的正 X 是「鼻子朝下」，所以往上瞄是負值 ——
這在兩種模式下都成立，任何一發射擊都會把頭轉到槍管的方向上去。

身體的分配是在**排定射擊的當下算好一次**，不是每幀重算。這裡踩過一個坑：
一邊每幀重算「還差多少的 25%」、一邊又用「剩餘時間的比例」去緩動，
身體會反覆追著遞減的餘量跑，最後轉的量遠超過它該分到的。
固定距離、按剩餘時間比例前進，才會剛好在延遲結束時到位。

瞄準的權重是**快進慢出**：射擊在轉身結束的那一刻發生，頭還在追的話就等於沒瞄；
放開之後才慢慢飄回步態。

**點到空處不發射。** 未鎖定時「點擊就是瞄準」，所以點在空處等於沒瞄任何東西 ——
為一次手滑花掉一發並不合理。鎖定時沒有這種情況：準心永遠指著某個地方。

轉身**最多**需要 0.15 秒，射擊因此有延遲。那個延遲**不是要被壓低的成本**：
光束若在動物還沒看過去之前就射出來，讀起來像瞄歪了，而不像反射動作。

但延遲是**那個轉身**，不是一筆過路費：已經在看著目標的貓沒有頭要轉，
所以延遲按「實際要轉多少」縮放。否則對著正盯著的目標連發會一直卡頓。

指標被鎖定時不用等 —— 那時貓本來就正對著準心。

扳機是**狀態轉換**不是事件：pointer 層可能把同一次按壓回報兩次（它會自我修復
「第一個 move 事件就已經按著」的漏接），以按下本身上膛會一次射兩發。

未鎖定時滑鼠還要負責繞行鏡頭，所以那裡是「沒有拖曳的點擊才算一發」；鎖定時滑鼠沒有別的工作，
才能按住連發。

**畫的，不是行進出來的。** 一道雷射只有幾公釐寬而且完全筆直 —— 那是 sphere tracer 最不擅長的
形狀，每條射不中的射線還是得付出代價。當成兩片面片就只是 12 個頂點。

畫兩道是因為有兩隻眼睛，但**物理只用中間一條軸**：兩眼在一隻一公尺高的動物上只差幾公分，
沒有任何值得計算的衝量分得出來。

遮蔽是白拿的：讀場景那條深度 alpha（撞擊閃光用的同一條），所以有東西擋在前面時光束會被切掉。

但**光是深度測試不夠**：它只會把「有東西更近」的地方藏起來，那不等於讓光束停下。
穿過球體的光束會在球內被正確藏住，然後從另一側**冒出來繼續射向天空** ——
那讀起來像從星團後面經過，而不是打中它。所以射程是開火時用 CPU 走一次同一個場量出來的
（地板是平面，直接解交點）。

### 兩個非顯而易見的坑

**不能用世界空間的 billboard。** 直覺做法是 `cross(光束方向, 朝向眼睛)` —— 在這裡剛好完全錯誤：
雷射是**沿著準心**射出去的，所以它幾乎與視線平行，那個外積會塌成零，面片寬度變成 0、整道雷射看不見。
改成沿**投影後**的光束方向取垂直，就沒有退化情形，而且得到固定像素寬度 —— 雷射本來就長那樣。

**一次按壓只能是一發。** pointer 層可能把同一次按壓回報兩次（它會自我修復「第一個 move 事件
就已經按著」的漏接情形，而合成事件也會兩者都送），所以以「按下」本身當扳機會一次射兩發。
扳機是那個**狀態轉換**，不是那個事件。

### 漣漪的中心從點變成線

一次點擊留下的是**點**衝擊，波以球面從那一點盪開。一發雷射留下的是**線段** ——
它穿過的整段距離 —— 同一個波就以**圓柱面**從那條線盪開，於是打開的是一條貫穿的通道，
而不是一個「它剛好先碰到哪裡」的坑。

衝擊從一個點變成一個**線段**。長度為零的線段就是點，clamp 會自動處理，所以質量消散那一段
點擊和雷射走的是完全同一段程式碼。

**但波的方向要分開。** 一開始兩者都用「點到線段的距離」當波前，結果雷射會從光束**側面**
把波徑向甩出去 —— 那是點衝擊的行為，而光束不往旁邊推任何東西，看起來就是錯的。
所以貫穿的波前改成沿**軸向**量，在生命週期內從入口掃到出口，再加一個徑向衰減把它關在
自己鑽出來的洞裡。點衝擊維持球面擴張不變。

**消散強度也分開。** 一次點擊是凹陷，一道雷射必須貫穿 —— 洞得比它要穿過的壁還深。
強度存在線段另一端那個沒用到的分量裡（`uRippleTo[i].w`），點擊是 1、雷射是 4。
消散量因此**不再夾在 1**：夾住的只有「用來讓波靜音的遮罩」，深度是原始值，
而那正是「打穿一顆球」和「在上面壓一個凹痕」的差別。

追蹤器的步長上限是從消散的梯度推導的，所以那個 4 倍也得餵進去 ——
但是**用當下真正存在的最大強度**，不是編譯期常數：否則每一次普通點擊都要用雷射的步伐前進，
白白慢一倍。

線段是「光束被星團包圍球裁切後的那一段」，也就是它唯一可能在任何東西裡面的那一段。
它**釘在世界座標**上，不像點擊那樣掛在某顆球上跟著公轉：貫穿的通道穿過的是「當時擋在路上的東西」，
沒有哪一顆球擁有它。

雷射因此**不會停在第一個表面**。它會穿過去、從另一側出來，而它鑽開的通道正是讓你看見它穿過去的東西。
唯一會終止它的是地板，那是一個平面，直接解交點。

### 柔軟的尾巴

尾巴不是棍子。牠被身體帶著走，而且**越靠近尾梢的點，越晚才知道身體動了**。

做法是一條彈簧鏈：9 個節點，每一節被更靠近尾根的那一節拉著。這個拉力是**單向**的 ——
後面的節點永遠不會反過來拖前面的，所以身體主導、尾巴跟隨，而不是兩者互相拉扯。
延遲沿著鏈累積，柔軟感就是這樣長出來的，沒有人手寫過一條延遲曲線。

原模型每幀在 CPU 上變形尾巴的頂點再重新上傳。這裡改成**只把鏈送過去** —— 9 個節點的偏轉角，
一個 `vec2[9]` uniform —— 由 vertex shader 依每個頂點烘焙好的「outerness」（尾根 0 → 尾梢 1）
自己內插。這個 outerness 藏在 normal 的第四個分量裡：三分量的 snorm16 attribute 本來就會被
驅動程式補齊到四個，所以讓尾巴變軟的那個通道，以 byte 計是免費的。

鏈的驅動來源是**世界朝向**，不是骨頭：這裡的轉身發生在 model matrix 上，
如果只看骨頭，過彎時尾巴會是死的 —— 而那正是真尾巴甩得最開的時候。

尾巴的**朝向**也改了。模型裡的弧線在 XY 平面，也就是往身體側面翹；
那在鎖定的四分之三視角下讀得出弧度，在自由視角下就只是一條往旁邊伸的尾巴。烘焙時繞 Y 轉四分之一圈，弧線就落到 YZ 平面，
從任何角度看都是往身後掃上去。這個旋轉烘進頂點而不是加到骨頭的靜止旋轉上 ——
它必須作用在姿勢**之後**，否則會把甩動軸一起帶走，尾巴就變成前後擺了。

### 鬍鬚：一個「把樞紐變成骨頭」的做法

鬍鬚和尾巴一樣在模型的可彎曲清單裡，但它們**繞臉頰上的一個樞紐彎**，不是繞自己骨頭的原點 ——
而 shader 只會繞骨頭原點轉。這正是它們一開始沒能跟尾巴一起做的原因。

解法是**給每根鬍鬚一根自己的骨頭，放在它的樞紐上**。沒有任何東西會擺動這 6 根骨頭，
它們純粹是為了「把原點放到對的位置」；放好之後，鬍鬚就跟尾巴共用同一套機制。

一根有樞紐的骨頭位於 `物件矩陣 · translate(樞紐)`，而這仍然是一個單純的 TRS ——
平移先被轉進物件自己的座標系而已。保持 TRS 形式，執行期就完全不需要為它們開特例。

驅動鏈也不同：鬍鬚跟**頭**，尾巴跟**身體**。所以貓只是轉頭而身體沒動時，鬍鬚會拖、尾巴不會。
臉的兩側在各自的局部座標系裡是**反號**的 —— 這樣它們在世界空間中才會往同一個方向拖。

每個頂點用哪條鏈，寫在骨頭那個 byte 裡：**低 5 bits 是骨頭索引，高 3 bits 是 sway group**。
沒有多花任何空間。（烘焙時會擋下超過 32 根骨頭的情況：無聲進位會變成一片三角形焊在錯的關節上。）

增益調高到 0.12（模型原值 0.05）：那個值適合「貓佔滿整個畫面」的近景，
這個場景是從更遠的地方看一隻更小的動物，0.05 在這裡的擺幅不到半度 —— 正確，但看不見。

### 骨架：沒有一個蒙皮權重

原模型是**剛體階層**動畫：每個部位是一整塊網格繞關節轉。所以不需要 glTF 意義上的骨架，
只需要 17 根骨頭的 TRS，和一次由父到子的前向遍歷。`bake-cat.mjs` 把骨頭之間所有靜態變換
**折進頂點裡**，執行期只剩 `applyPose` 真正會動的通道。

```
node tools/bake-cat.mjs                       # 三個花色，全部進同一個檔
node tools/bake-cat.mjs --skins orangin,tabby # 只要其中幾個
```

輸出 935 kB：position `f32`、normal `snorm16 × 4`（第四個分量是尾巴的 outerness）、
colour `sRGB u8` **每個花色一份**（骨頭索引就藏在第四個 byte 裡）、index `u16`。

三個花色**只有調色盤不同** —— 同一組頂點、同一組法線、同一份索引、同一副骨架 ——
所以幾何只存一次、調色盤存三份，比三隻完整的貓省下將近一 MB，
而且換花色是**一次 buffer 上傳**，不是重新載入。烘焙會斷言這件事，不是假設它：
某個花色若偷偷改了頭部細分，它的顏色就會套到別人的頂點上，貓會變成紮染。
**這是一次性的離線步驟，app 本身仍然零依賴、零建置**；three 只是隔壁專案的 devDependency，
永遠不會被 ship。

### 一個名字騙人的 bug

四條腿的相位曾經是錯的：貓像搖搖馬一樣，同一側的前後腳一起往前擺。

原因不在相位，在名字。上游模型的兩對腿是從**相反的兩端**命名的 ——
`hindHips[s < 0 ? 'R' : 'L']` 對上 `frontPaws[s < 0 ? 'L' : 'R']` —— 所以 `hipHL` 在
x = +0.92，而 `pawFL` 在 x = −0.35。相信名字，就會把每條後腿和**同側**的前腳配成一對。

現在配對是依**靜止位置的 x 符號**決定的，不看名字。唯一能可靠說出一條腿在哪一側的東西是它的
座標；就算上游哪天把名字改一致了，這裡也還是對的。`--interact` 裡有一項專門盯著它，
而且是取整個擺幅的極值來測 —— 每個步態一個週期會兩次經過零點，在那裡量什麼都會過。

### 光影：兩個方向

### 嘴部皺褶：修法線，不是修光

換成連續打光之後，口鼻周圍浮出一道生硬的弧線。那不是光照的錯，是**幾何的問題被照出來了**：
模型把口鼻平台從球面推出去，而推的範圍是一個硬邊界的條件式，沒有任何羽化 ——
曲面因此連續、但它的**導數不連續**，`computeVertexNormals()` 忠實地回報了那道折角。

三階 ramp 把折角兩側量化進同一階，所以看不見；連續打光看得見，而高光更是主動在替它宣傳。

修法是**平滑法線、不動頂點**。剪影、描邊殼、陰影代理全部不變 ——
只放鬆「每個點宣稱自己朝向哪裡」，而那正是原本錯的那個量。兩道都走索引緩衝：

- **weld**：同一個位置的頂點共用一條法線。球面幾何為了 UV 會在接縫與極點複製頂點，
  那些複製品原本各自帶著不同的法線，等於在後腦杓上另外開一條縫。
- **relax**：每個頂點取「與它共邊的頂點」的平均，保留自己一半的權重 ——
  這一步才是真正把折角軟化掉的。

只套用在**有手工切痕的兩個形狀**：頭（口鼻平台推出去的地方）和身體（底部被水平切平）。
兩者都用頂點色上色，這正好把它們和掛在同一根骨頭上的純色部位分開 —— 鼻子也在頭骨上。

**高光同時換成 sheen。** 毛皮不是拋光表面，不該有拋光表面的高光；它該有的是掠射角的絨光。
而且「寬」是重點：一個銳到能被讀成高光的 Blinn lobe，等於把內積取到約 28 次方 ——
那是個**誤差放大器**，會把相鄰法線之間的小小分歧變成一道可見的接縫。
sheen 是掠射項的低次方，面對同一組法線安靜得多。

沒有再加 wrap diffuse：做完上面兩件事之後明暗交界已經夠平滑，再軟化只會把立體感一起糊掉。

貓**不再用模型自帶的三階量化打光**，改用場景自己的那一套，逐項相同：
Lambert 漫射 × 主光 × 陰影、藍灰色環境光、Blinn-Phong 高光（指數由粗糙度導出）、
Fresnel 天空反射、距離霧。毛皮的參數是「很粗糙、非金屬」，所以高光是一片寬鬆的光澤而不是亮點。

模型自帶的 cel ramp 適合「貓就是整張畫面」的情境，平塗是那時的重點。
在這裡牠只是被同一顆太陽照到的其中一個物體，而只把牠的漫射量化，
會讓牠變成畫面上**唯一一個對光線反應不連續**的東西 —— 不管陰影做得多好，那都會讀成剪貼。

**黑邊留著。** 它們是墨線，不是明暗；打光停止「被畫出來」之後，正是它們維持住手繪感。
眼睛、鬍鬚、嘴也一樣保持平塗。

**陰影也是同一套。** 星團的整個分層距離場（含漣漪、質量消散、表面擾動）都從 march.js
搬進 `scenes/cluster.js`，兩邊呼叫**同一個** `clusterShadow()`、走同樣的分層、同樣的步數預算。
走比較簡單的場的陰影，等於是另一個略有不同的物體的陰影，而兩者**正好會在場景最活躍時分開**。

射線從開闊地面出發時幾乎立刻離開星團的包圍球，所以在野外成本就是一次 miss；
背對光的面根本不發射線。貓**不自我遮蔽** —— 牠的膠囊是粗略近似，有些地方會戳出真實表面之外，
拿它們自我遮蔽只會得到一片 acne。

**貓遮住地板。** 7 根膠囊掛在同一副骨架上，進到 shadow 與 AO 查詢裡。
它們在每個細節上都是錯的、在輪廓上是對的 —— 而陰影要的就只是輪廓。

**刻意不進主射線**：畫出畫面的射線仍然只看到星團，否則會有一隻糊糊的第二隻貓站在真的那隻裡面。
代理只服務「路上有沒有東西」這種問題，而那種問題分不出膠囊和貓。

### 一次值得記下的連結失敗

貓的陰影原本是用**行進**解的，結果 shader **連結失敗，而且 log 是空的**。

原因是 `softShadow` 會被編譯器內聯兩次（主射線一次、反射彈跳一次），多一個迴圈就撞上
D3D `ps_5_0` 的指令上限。空的 log 沒有給任何線索，所以是靠二分法找出來的：把膠囊數降到 2
仍然失敗，把那一行呼叫註解掉就過 —— 於是知道是「複雜度」而不是「數量」。

改成**解析解**之後就好了：軟陰影本來就是「射線最靠近遮蔽物的距離 ÷ 走到那裡的路程」，
而對一堆膠囊來說，那個最近距離有閉式解（射線對線段的最短距離）。完全沒有 t 迴圈，
每根膠囊只要幾個內積。而且這個答案**嚴格更好** —— 取樣式的行進可能一步跨過腿最細的地方。

星團用行進、貓用解析：同一個問題的兩種答案，各自對自己的形狀最便宜。

## 地面

面板「地面」分組。地板造型只有**兩種**，**「網格」是預設，而且一行都沒有改** ——
它是這個場景的基準面，說明地板在哪裡。

| 造型 | 內容 |
|---|---|
| **網格**（預設） | 原本那片帶淡格線、會隨距離淡出的地板 |
| **草地** | 立體草葉，隨風擺動（[src/scenes/ground.js](src/scenes/ground.js)）|

長在上面的東西各自是一個開關加一支密度滑桿：**花**（同上）與**樹**
（[src/scenes/trees.js](src/scenes/trees.js)），兩者預設都關。

花原本是第三種「造型」，那是個分類錯誤：它不是另一種地板，它是長在草地上的東西 ——
跟樹一樣。分成造型之後就沒辦法要「草地加樹但不要花」，而那是完全合理的一種要求。

### 為什麼草不在距離場裡

地板是一個閉式解的平面，這是它幾乎不花錢的原因，也是它種不出東西的原因：
把十萬片草葉放進距離場，等於讓 sphere tracer 為了走到地面而經過每一片。

所以草根本不在場裡。它是**三角形**，畫進貓那張 target，用同一行深度比較去解 ——
就是上面那條交接。**沒有任何 mesh**：一片草是 7 個由 `gl_VertexID` 推出來的頂點，
一朵花是 48 個，沒有一個是載入來的。

草**連存都不存**，每幀從它那格的雜湊重新推導 —— 兩次 hash 攤在 7 個頂點上，比去記憶體
抓還便宜。花**存**，因為對花來說不是：見下面。

### 草皮跟著鏡頭走，草不跟

固定大小的草皮不是小到看得見邊，就是大到畫不動。所以格線**中心跟著鏡頭**（並往視線方向
推，把預算花在畫面裡而不是背後），而且**每一環各自對齊自己的格寬**；每一片草的位置、高度、
朝向都是從它那格的**世界座標**雜湊出來的。

格線在滑動，草沒有。種子若是跟著 instance 編號走，整片草原會隨著你走路而在地上爬行。
邊緣不是淡出也不是消失，是**縮回地裡** —— 唯一一種沒有東西可以彈跳的收邊。

`--interact` 有一項在守這件事：草皮原點永遠落在自己的格點上（偏差 `0.0e+0`）。

### 風是一個場，不是一段動畫

一個關於位置與時間的函數，草和花莖讀的是**同一份**。所以一陣風是以單一事件的形式
掃過整片地，而不是每株植物各自播放自己的擺動；花會跟著它周圍的草一起倒。

彎曲是**旋轉**，不是剪切：角度隨高度的平方成長（根部硬、接近尖端才給），每個點到根部的
距離不變。剪切過的草葉會愈倒愈長，而「整片草在風中一起變長」是把風做錯的最明顯徵狀。

### 第一版是一片焦黑的釘子

直立的草葉，法線是水平的。太陽在天上任何位置時，有一半的草原是背對它的 —— 於是全黑。
第一次算出來的畫面就是一整片燒焦的鐵釘。

眼睛不會把草坪讀成一百萬片直立的平面，它讀成一個**表面**，而那個表面朝上。
所以法線往正上方偏（`SWARD_BIAS`），草叢的形狀就退回成那個表面上的變化，而不是全部的訊號。
另外草只有一個細胞厚，背光時會透 —— 那道透光是「草原」和「一堆綠刺」之間的大半差別。

同一個道理讓草底下的土是**綠的而不是棕的**：沒有任何 instance 預算能讓每平方公分都站一片草，
所以縫隙露出來的東西必須跟站在裡面的東西同色 —— 是俯視的深色草皮，不是底下的泥。
棕色的地會讓稀疏的草變成犁過的田上的殘株。

### 花是按叢種的

一個 4 公尺的粗格，每格擲一次骰決定長不長；叢裡的花往中心堆，並**往邊緣愈來愈稀** ——
出來的是「密的中心加上周圍幾株落單的」，而不是一塊有邊界的花圃。一叢是一個品種，
所以顏色是按叢雜湊的。

那三件事各自是一支滑桿：

| 滑桿 | 控制 |
|---|---|
| **花叢密度** | 有幾叢（那一次擲骰的門檻）|
| **叢內花密度** | 一叢有多少朵 |
| **花叢範圍** | 同樣的花攤在多大一片地上 |

前兩支分開，是因為它們是兩張不同的畫面 —— 疏落的幾叢濃花，和撒滿整片地的稀花。
一支滑桿到得了兩端，卻永遠說不出自己正在做哪一種，而中間那些設定才是真正好看的。

實測：兩支都拉滿 716 朵；只把叢數砍到 0.3 剩 234 朵；只把叢內密度砍到 0.2 剩 145 朵 ——
數量接近，畫面完全不同。

第三支是**異類**：前兩支拿走花，它是把**同樣的花攤到更多地面上**。拉小是緊實的一球，
拉大到叢與叢重疊，就變成連續的散花。實測 `275 朵散在 20 m²` 對 `277 朵散在 137 m²` ——
數量幾乎不動，面積七倍。

拉大範圍時，播種要多看**一圈格子**：一個坐在可視格子外的寬叢，仍然會把花丟進格子裡，
漏掉它們會在邊緣稀掉一圈 —— 範圍 1 時看不出來，一旦叢有好幾公尺寬就很明顯。

花的作用半徑比草**短**（0.62 倍，封頂 60）：一片遠處的草還有意義，因為它貢獻的是
遠景的**顏色**；那個距離的一朵花不到一個 pixel。封頂的理由不同 —— 叢格固定在 4 公尺，
所以花的數量隨視距的**平方**成長，超過那裡播種緩衝區會先於圓被填滿。

播種是**由近而遠**的（格子偏移量先按距離排序）。緩衝區真的滿了的時候，該掉的是四面八方
的遠處，而不是像逐列掃描那樣掉掉某一條線以後的全部。

花莖被刻意做得比草高一截。頭跟草齊高的花是永遠不會被看到的花 —— 除了正上方，
草皮從每個角度都會蓋過它。

### 花只算一次（一個真 bug）

第一版把上面那整串 —— 這格長不長、叢心在哪、叢多寬、這朵有沒有被稀掉 —— 寫在
vertex shader 裡。它有兩個問題，一個是浪費，一個是錯的。

**錯的那個**：花的格子是 4 公尺一格，但整個草皮的原點只對齊 **0.5 公尺**的草格線。
於是相機每走半公尺，花格的角點就換一個位置，整叢花被重新擲一次骰 ——
**花的位置一直在變**。草是對的（它的格線就是那 0.5），花不是。

**浪費的那個**：一朵花有 48 個頂點，每一個都要把那整串算完，得到同一個答案；
而那個答案每一幀也都一樣。

現在改成**在 CPU 上播種**，只在草皮原點移動整整一個花格時才重算 —— 走直線大概每幾公尺
一次，站著不動則永遠不會。結果丟進一個 instance buffer，vertex shader 只讀。
被稀掉的花根本不會進 buffer（以前是進去了才在 shader 裡丟掉，白跑一趟 vertex shader）。

播種用的雜湊是**世界格座標的函數**，跟草的道理一樣 —— 所以重播之後，兩份 buffer 共有的花
會落在**完全相同**的座標上。`--interact` 有三項在守這件事：站著不動不重播、
拖曳整段鏡頭只重播一次、而且 257 朵裡有 206 朵位置一致到 0.1 mm。

唯一不能預先算的是**邊緣淡出**：那是從眼睛「現在」的位置量的，而眼睛是連續移動的。
那留在 shader 裡，一個 `length()` 加一個 `smoothstep`。

### 視距：加的是面積，不是尺寸

「一望無際的草原」和「把幀數還我」是同一個滑桿的兩端（8–120 單位）。

第一版是**一個格線、格寬隨視距開根號變大**。成本確實壓下來了，而且完全錯：
放大格寬等於放大整個圖樣，所以視距一拉遠，**腳邊的草就變稀**。
要的是更多草地，拿到的是同一片草地被放大。

所以近處的格寬**永遠不變**。距離是靠往外加**環**買來的 —— 一圈圈同心方形帶，
每一圈比裡面那圈粗，中間挖掉裡圈已經蓋過的部分。**第 0 環在任何設定下都是同一片草坪。**

環的粗細比不是寫死的 2，是解出來的：`step = (視距 / 16)^(1/(環數-1))`，
好讓最外圈**正好**落在要求的視距上，而不是跳到下一個 2 的冪 —— 滑桿因此是連續的。
挖洞時往內縮一格，讓環之間**寧可重疊也不要留縫**：兩圈各自對齊自己的格寬、邊界不會對齊，
重疊一條帶子看不出來，留一圈裸土則是災難。

成本隨**環數**成長，也就是視距的對數：

```
8 單位   → 1 環 / 16,384 片草
120 單位 → 5 環 / 81,920 片草      15 倍視距，5 倍的草
```

而且 8 單位和 120 單位用的是**同一個 0.5 格寬**。`--interact` 兩項在守這件事。

實測 120 單位是 20.2 ms —— 跟舊版 44 單位一樣的成本，多看了將近三倍遠。

花的叢格同理固定在 4 公尺，改成**限制它能走多遠**（34 單位封頂）：
遠處的草還貢獻顏色，遠處的花頭連一個 pixel 都不到。

### 遠處付得比近處少

視距拉遠之後，外圈的草開始佔掉大半的頂點，而那些草在畫面上只有幾個 pixel。所以**每一環各發一次 draw**（最多五次），因為「一片草值幾個頂點」和「值不值得問陰影」都不能在單一 draw 裡變化：

- **第 1 環以外，一片草是一個三角形**（3 頂點，不是 7）。失去的是沿長度的彎曲 —— 那是草的側影的全部，而二十公尺外一片草只有兩個 pixel，沒有側影可以失去。
- **第 2 環以外不問陰影**。那裡開始霧已經吃掉大半顏色，而每片草原本都還在做一次星團包圍球測試加五次樹影取樣。兩個陰影項都把 0 讀成「不用問」並在一個比較內返回，所以關掉不需要 shader 分支、也不需要第二個 program。

**實測**（`--bench`，同一次執行內對照 `full-res`）：

```
之前  full-res 15.7 ms   grass far 19.7 ms   → 草多花 +4.0 ms (+25%)，frame 27.0 ms
之後  full-res 15.9 ms   grass far 17.7 ms   → 草多花 +1.9 ms (+12%)，frame 20.8 ms
```

遠景草的成本**砍半**。

一個踩到的坑：第一版把整組 uniform 交給每一次 draw（`{...common, uRing}`），結果**比原本的單一 draw 還慢** —— common 裡有星團的球、四個撞擊、八根貓膠囊和相機，一幀重傳五次比省下的頂點還貴。改成不變的部分上傳一次、每環只傳四個。

### fragment shader 幾乎是空的

草在畫面下半部疊了好幾層深，所以 fragment shader 裡的任何東西都要為了一個幾 pixel 高的
東西付好幾次。光照和霧都改在**逐頂點**解決（霧裡那個 220 次方尤其貴），
fragment 只剩一件事：把花心的方形四角丟掉，讓它在畫面上是圓的。

## 樹

面板「地面」分組的「樹」開關（預設關）。程式在 [src/scenes/trees.js](src/scenes/trees.js)。

分工是整個設計：**CPU 長骨架，GPU 長幾何**。遞迴分枝在 JS 裡是一個帶堆疊的巢狀迴圈，
在 vertex shader 裡是一道算術謎題 —— 花那次已經學過一遍。但「一節樹枝展成一段錐管」、
「一片葉展成一張有輪廓的卡片」是頂點編號的純函數，那該在 GPU。
所以 CPU 只寫**線段與附著點**，這個檔案裡沒有任何地方組出過一個三角形。

### chunk：生成比儲存貴的東西才切

一棵樹約一百段樹枝、三百片葉，長一百棵要幾毫秒 —— 每次視野一動就重算會看得到卡頓。
所以世界切成固定 **16 公尺**的 chunk，各自長一次、留著，移動只付新進範圍的那幾塊。

chunk 大小**固定在世界座標**，刻意不隨視距縮放：縮放的話改一次視距全部作廢，
固定的話只是載入／卸載外圈，已經長好的原封不動。而且**永遠多長一圈**，
所以世界的邊緣不會是「已經長出來的東西」的邊緣。

`--interact` 守著這件事：拖曳整段鏡頭之後，已經長過的 chunk 一塊都沒有重長。

### 位置：抖動子格，不是丟飛鏢

每個 chunk 切成 2×2 個子格，每格至多一棵、在格內抖動。這一個選擇同時給了三件事：

- **每個 chunk 的數量上限**是 4，不是全圖上限 —— 所以 buffer 裡每塊的位置有固定界線
- **最小間距**由構造保證：抖動範圍是子格的 ±28%，所以兩棵樹永遠不會近於 **3.5 公尺**
- 而且**跨 chunk 邊界也成立**，任何一塊都不需要去問鄰居 —— 這才是 chunk 能任意順序生成、
  各自丟棄的原因

星團周圍 **6 公尺不長樹**：樹會插進球體和星環裡，而且主體會有一半時間躲在樹幹後面。
林間空地剛好也是森林最自然的樣子。

### 樹幹與分枝

遞迴參數化，不是 L-system —— 要的是對輪廓的控制，不是文法。三個讓它像樹的細節：

**達文西定律**：子枝截面積和 ≈ 母枝截面積，也就是 `r_child = r_parent / √n`。
這一條比任何噪聲都關鍵；隨手挑的收細比例會讓樹讀成塑膠。

**根部外擴**：底部十分之一急速變粗。這是「長出來的樹」和「插上去的桿子」的差別。

**截面不是圓**：環頂點半徑乘上兩個低次諧波，每棵樹的葉瓣數與相位不同。
一個角度的函數，成本是兩個 sine，幾何上完全免費。

彎曲是加在**方向**上而不是頂點上：推頂點得到一根有疙瘩的直枝，推方向得到一根會遊走的枝。

管子的環座標系是 CPU 沿著枝條**平行移動**下來的。在 shader 裡從世界軸重建是直覺做法，
而且錯兩次：在垂直的樹幹上會退化，而且每一節都會轉一點，於是樹皮的葉瓣對不齊、每個關節都是縫。

### 葉：一個連續的輪廓族

沒有貼圖。半寬由 `pow(sin(π·t^skew), sharp)` 給，兩個指數：
第一個移動最寬處（低＝靠近葉柄最寬，高＝過中線才最寬），第二個決定尖不尖。
兩者一起涵蓋卵形、披針形、倒卵形之間的全部，所以**同一棵樹上沒有兩片葉是同一個形狀**，
而且不花任何一次分支 —— 形狀是從葉子自己的位置雜湊出來的，不用存。

**中脈摺**是必要的：沿葉脈把截面折成淺 V。平的葉在任何距離都讀成紙片；
折過的一半接光一半在陰影裡，那是樹冠看起來有厚度的全部原因。

一片「葉」其實是一叢手掌大的簇葉，不是一片植物學上的葉子。真實比例下，四公尺的樹上
一片葉是十公分，三百片只蓋掉樹冠的百分之二 —— 第一版長出來的是一片冬天的枯枝林。
Instance 預算能買覆蓋率或買植物學，在任何看得到的距離上，能讀成樹的是覆蓋率。

### 葉子的 LOD：少而大

五十公尺外的樹原本和眼前的樹一樣揹著四百片葉，而那個距離整個樹冠只有三十個 pixel。

丟掉的是**數量**，補回來的是**尺寸**：CPU 依距離只打包每個 chunk 的一段前綴，vertex shader 把留下來的葉子乘上同一條曲線的**倒數平方根** —— 因為覆蓋面積正比於「數量 × 尺寸²」，這樣縮放剛好讓樹冠的密度不變。二十公尺外「少而大」和「多而小」人眼分不出來。

兩個實作細節是必要的：

**葉子在 chunk 長出來時就被洗牌**（Fisher-Yates，種子來自它自己的格子）。不洗的話，取前一半等於取到前兩棵樹的全部、後面幾棵一片都沒有。

**太陽那一遍也要用相機的 LOD**。光空間的 vertex shader 因此收到 `uCamPos` —— 看起來像 bug，其實是必須的：影子要由**眼睛實際看到的那組幾何**投出來，用全細節的葉子畫出來的影子，遮的是一個不存在的樹冠。

實測：預設鏡頭下 **26,486 片葉只畫 9,996 片，丟掉 62%**。時間上的省在測試視角看不出來，因為那個 case 已經頂到 48 fps 的上限 —— 但頂點數是精確的，而且弱 GPU 上省的就是這個。

### 風：附著點不會分開

形變是**靜止位置的純函數**：

```glsl
vec3 sway(vec3 rest, vec2 base, float flex, float phase)
```

葉子傳進**它附著那一點的 `flex` 與 `phase`**，加上自己的靜止座標，函數同一個、位移同一個 ——
所以葉子永遠黏在枝上，沒有骨架、沒有矩陣、沒有一個蒙皮權重。跟草的 `stalk()` 是同一個想法。
沒有東西需要保持同步，因為沒有東西被拆成兩份。

樹幹**只讀風的慢項**。一噸木頭不會回應半秒的抖動，而「各自濾掉什麼」正是讓尺度可讀的東西：
樹幹慢、枝條有自己的節拍、葉子則是全場最高頻的動作。風場本身是 [wind.js](src/scenes/wind.js)
的同一份，草、花、樹都讀它。

### 樹影：真的投影，有深度

樹從太陽那邊再畫一次，正交投影進一張 1024² 的貼圖：**紅色是覆蓋、綠色是沿光軸的距離**，
外加一個 depth attachment 做歸約。

便宜的做法是只存覆蓋率，它會以一種容易忽略的方式壞掉：沒有深度就分不清
「遮蔽物在我和太陽之間」和「在我後面」，於是每個樹冠內部都是一片死黑而不是斑駁的。
第二個通道只多一個 attachment，換到**自陰影**，以及**隨間距變寬的半影** ——
後者是讓樹影表現得像星團那道行進解出來的陰影，而不是宣告自己來自一張貼圖。

它在世界裡錨定、並**對齊自己的 texel**，所以走直線大概每幾公尺重畫一次，站著不動不重畫。
沒對齊的話，貼圖每幀滑動不到一個 texel，場景裡每一道陰影邊緣都會爬。
（風開著時每幀重畫 —— 樹在動，靜止的影子比沒有影子更糟。）

讀取是**一次 texture fetch 加四個 PCF 取樣**，不是往 `softShadow` 裡再塞一個解析圖元。
那個函數會被內聯兩次（主射線 + 反射彈跳），而且**上次就是在那裡撞上 D3D `ps_5_0` 的指令上限**。
一次取樣不管內聯幾次都是一個指令。

四個接收端讀它：行進出來的地板、草、貓、以及葉子自己。

### 成本

64 棵樹、5,460 段樹枝、26,486 片葉。近距離貼著樹冠看約 35 ms，一般構圖約 20 ms ——
和視距拉滿的草是同一個量級，而草仍然是比較貴的那一個。

## 湖

一座湖是**一個數字**：水面的高度。

它是一個水平面，而且刻意是。任何更豐富的表面 —— 第二張高度場、流場、真的去模擬 ——
買到的細節在這個場景唯一被觀看的十五公尺高度上看不見，卻要付掉讓水幾乎免費的那個性質：
**射線碰到水平面用一次除法，不用行進。**

讓它讀起來像湖而不是蓋在世界上的一片玻璃的，是另一條：**只有那一點底下的地更低，命中才算數。**
代價正好是一次高度取樣，在射線落點那一個點上。

```glsl
float traceWater(vec3 ro, vec3 rd) {
  if (!hasWater()) return -1.0;
  float t = (uWaterY - ro.y) / rd.y;
  if (t <= 0.0) return -1.0;
  return terrainH((ro + rd * t).xz) < uWaterY ? t : -1.0;
}
```

### 岸線不是畫出來的

它就是地形跟水面相交的地方。拉「地形起伏」或拉「水位」它都會跟著動，
而且**沒有兩個消費者能對它有不同意見**，因為每一個都是拿同樣的問題去問同一個場。

同一個性質讓播種完全不必知道「湖」是什麼概念：一顆種子只要 `waterDepth` 為正就是淹死了，
規則就這一條。三個消費者用三種方式回應，而三種方式的差別是它們**幾何上的差別**，不是三個決定：

| | 怎麼避開水 | 為什麼是這種 |
|---|---|---|
| 草 | 12 公分內漸漸縮進地裡 | 位置是頂點著色器從格子推出來的，沒有更早的時機可以不生成它；而且岸線以任意角度斜穿格子，硬切會把它切成階梯 |
| 花 | CPU 播種時整株跳過 | 一朵花是一個物件，半朵站在水裡就是一朵被攔腰切斷的花 |
| 樹 | CPU 生成時整棵跳過 | 一棵淹死的樹省下的是整段遞迴、160 個枝段與 400 片葉 —— 用四個正弦換掉 |

### 「關掉」不是一個旗標

水面退到地面能到的最低點以下，就是**沒有射線碰得到、沒有種子淹得死**的水。
所以 `hasWater()` 是一個誠實的測試而不是哨兵值比對 ——
而且同一個測試順便讓「地形起伏 = 0」的平坦世界免費地沒有水
（平地和水面共面，「誰在前面」沒有逐幀穩定的答案）。

### 水位滑桿：線性於面積，不是線性於深度

第一版是深度，而深度是錯的。地面是正弦的和，高度會堆在中間、在兩端變稀 ——
所以一支線性於深度的滑桿，下半段都在把水面移過幾乎沒有地到得了的高度。實測在真的場上：

| 淹沒比例 | 需要的深度（單位：起伏振幅） |
|---|---|
| 2% | 0.785 |
| 10% | 0.565 |
| 20% | 0.399 |
| 40% | 0.132 |
| 50% | 0.001 |

所有像樣的湖都擠在滑桿頂端五分之一：0.45 是水窪，0.95 才第一次讀起來像水。

現在滑桿說的是**面積**：0 是幾個深窪積水（2%），1 是接近四成的開闊地。
深度由分位表反推，而那張表是載入時從同一張 `WAVES` 現場取樣算出來的 ——
不是打進去的第二份真相，改一個波長它自己跟著變。

水位是**相對於起伏**的：同一個 level 在一公尺和八公尺的丘陵都淹掉同一比例的草原。

### 水面本身

沒有模擬、沒有折射。賣掉一座湖的只有兩件事，而這裡兩件都在：

**淺處看得到底，深處看不到。** 一個數字（`clarity = 1 - exp(-d × 2.1)`）就讓岸線不需要任何幾何 ——
水底在頭半公尺內自己淡出視線。

**表面夠光滑，讓 `main()` 本來就在射的那道反射彈射落得上去。**
所以這裡**沒有任何反射程式碼**：水只是這個場景裡第一個光滑到值得用那道既有彈射的表面。

法線由四道交叉波列擾動，平面仍然是平面 —— 湖面幾乎全是反射，而反射只是法線的函數，
擾動法線就買到整個外觀，`traceWater` 也還是一次除法。波列隨距離淡出，理由和這個場景裡每一個細節一樣：
比一個像素還細的波紋不是波紋，是時間濾波器接下來要花好幾幀跟它吵架的雜訊。

## 天氣

晴、雨、雪。**三選一，不是三支滑桿** —— 它們不是同一件事的三種量：
雨把地弄濕、雪把地蓋白，一個能給你「一半雨加一半雪」的控制是沒有人能拿來問問題的控制。

`weather.js` 裡放的是**場**（一個點上積了多少雪、地有多濕）和**落下來的東西**。
消費它們的一切都留在原地：土的顏色在行進器裡、葉片在草裡、播種在花裡。
這個切分就是整個設計 —— 一個自己帶一份地面的天氣，就是「地在哪裡」的第二個答案，
而那正是這個場景一輩子拒絕擁有的東西。

### 雪刻意不去做的事

第一版去抬高地形：雪是一層，一層有厚度，高度場就在旁邊。結果它付掉了地面賴以存在的那個性質。

`terrainAt` 是對著一個**斜率上界**被行進的，而那個上界是波表上的封閉形式和。
會隨坡度變化的雪，加進去的是那個上界完全不知道的梯度 ——
於是要嘛為所有人放寬上界（連晴天的長影子也一起變慢），要嘛行進overshoot、丘陵上開洞。

**而且它什麼也沒買到。** 雪在一片丘陵有公尺高、從十五公尺外看的地上積個幾公分；
那點抬升在任何會付到它的距離上都看不見。真正讀起來像雪的是：地是白的、草被埋了、有東西在落。

所以雪是**覆蓋率不是高度**，斜率上界一動不動。

我原本擔心的岸線問題在改成覆蓋率後**原封不動地還在**，也正是 `snowCover` 仍然要問水在哪的理由：
無視湖的雪會在水的頭半公尺上漆出一圈浮著的白。它改成隨著地面接近水面而收到零 ——
那也正好是積雪在水邊真正的樣子。

```glsl
float snowCover(vec2 p) {
  vec2 g; terrainAt(p, g);
  float hold = 1.0 - smoothstep(0.45, 1.15, length(g));   // 陡坡留不住
  float dry  = smoothstep(0.0, 0.50, -waterDepth(p));     // 岸邊收到零
  return uSnow * hold * dry * (0.72 + 0.42 * mottle);     // 斑駁，不是一層漆
}
```

三個因子，每一個少了都會以一種**具體的方式**出錯：沒有坡度項，丘陵是被上了釉而不是積了雪，
每個面不管朝哪都一樣白；沒有岸邊項，湖的第一圈浮著白邊；沒有斑駁，它就是一層漆 ——
真正落下的雪在被風掃過的地方薄、在背風處堆。

`snowCoverAt()` 是同一件事的 JS 版，同一張表生成，因為著色器決定一塊地看起來有沒有被埋、
而花的播種決定那裡的花有沒有被埋。**兩邊不一致就是花開在雪堆上。**

### 落下來的東西

一顆雨滴和一片雪花是**同樣六個頂點**。分開它們的是掉多快、沿自己速度被拖多長、以及裡面畫什麼形狀 ——
三個數字，所以它們是三個數字而不是兩支程式。

沒有屬性、沒有緩衝區。每一滴的位置是它自己索引的雜湊，被時鐘推進、被摺回一個跟著眼睛走的盒子 ——
所以場是無限的、沒有東西被生成或退休，CPU 的全部貢獻是一次 draw call 裡的一個頂點數。

風是**既有的那個場**（`wind.js` 的 `WIND_DIR` 與 `slowGust`），不是第二份：
所以掃過草地的那陣風，和穿過它落下的那陣雨，是同一陣風。
雨被吹得比雪硬得多 —— 一滴在空中待一秒、斜著到；一片飄半分鐘、到哪都有可能。

畫在 tonemap **之後**、加色混合，和撞擊閃光與雷射同一個位置。這不是對順序偷懶：
落下來的東西又小又快又亮，把它送進時間濾波器只會把每一滴抹成灰糊 ——
那個濾波器的工作就是收斂在**沒有在動**的東西上。

它讀的深度是**行進的與光柵的兩者取近**。只對行進深度測試的雨滴，會直直穿過畫面裡每一根樹幹。

### 雪為什麼要調暗

第一版的雪拍出來是**沙丘**。這個場景的太陽是琥珀色、tonemap 又大方，
照實際亮度寫下去的雪出管線之後是奶油色。

雪之所以亮是因為它**被照亮**，不是因為它的 albedo 接近 1。給它藍灰的 albedo、剩下的交給太陽，
問題就回去了 —— 而且要壓在直接項那個 2.3 增益不會削頂的範圍內，
否則每個受光面飽和成同一個平值，而**一片沒有明暗漸層的雪原沒有任何東西還能說明它是雪而不是紙**。

現在受光面被琥珀太陽照得偏暖、背光面落到偏藍的環境光 —— 那個對比才是眼睛在叫某個東西「雪」時真正在讀的。

## 日夜

一個數字進去 —— **時刻** —— 出來的是這個場景本來就在讀的四樣東西：光從哪來、什麼顏色、有多強、天上還有多少日光。

**下游沒有任何一支著色器學到「有時間這回事」。** 行進器還是讀一個方向和一個 tint，草還是讀同樣那兩個，天空多讀一個 float。這就是它付得起的全部理由：日夜循環通常是以「第二套打光模型」的形式到達，然後場景裡每一個表面都有兩種被照亮的方式、外加一個決定用哪種的參數。這裡它是**既有 uniform 的一個生產者**。

### 三個狀態，一個控制

場景本來就有光源方向（一個 XY 盤），而時刻是同一個問題的第二個答案。與其讓兩者互相搶，不如直接說明誰在管：

| | 誰在管光源 |
|---|---|
| **固定** | 方向盤，和這個檔案存在之前一模一樣。舊網址、舊參考截圖全部仍然成立 |
| **指定時刻** | 時刻滑桿。方向盤變成過時的讀數 —— 和「能見度」與「植被視距」的關係一樣 |
| **自動循環** | 同上，而且時刻自己會走（一天 130 秒） |

**三個模式而不是兩個開關**，因為它們不是兩個獨立的是非題：「方向盤在管」和「時鐘在管」不可能同時成立，一對開關是一個可以被設到沒有意義的狀態的控制。

時刻是被**模擬時鐘**推進的，不是牆上時鐘 —— 所以暫停會停住太陽、`.` 會讓它走一格。一個凍結時還在轉的場景，是一個參考截圖不可重現的場景。

### 太陽下山之後

它下山，月亮從對面升起。兩者是**同一道弧讀正讀反** —— 一個天體份量的算術供兩個天體用，所以它們不可能走散。

黃昏時換的只是那一個 `uLightDir` 指著誰。**換手看不見**，因為它發生在兩者都在地平線上的那一刻，方向項已經降到零 —— `--interact` 有一項專門守這件事（18:00 時光源離地平線 `0.0000`）。

順帶掉出來一件事：**午夜的月亮在正午太陽的同一個方位。** 看起來像 bug，其實是定義 —— 跟太陽相對的月亮就是滿月，而午夜的滿月正好在正午太陽的位置。它是從一道弧倒著讀出來的，不是被擺過去的，所以不用瞄就會對。斷言在守這件事，而且我第一版的斷言寫錯了、程式是對的。

### 低角度的太陽也要變暗

不只是變紅。只改色相的夕陽讀起來像一盞有顏色的燈；讓它讀起來**低**的是整片地同時暗下去。

```
sunUp:  strength = 0.22 + 0.78 × high        // high = 天體升到多高
        tint     = mix(DAWN, NOON, high) × strength
```

天光（`uDay`）刻意比太陽自己的橫越**更寬**：太陽落到地平線下之後天還會亮一陣，因為天是被空氣照亮的而不是靠視線 —— 一個在太陽碰到地平線的瞬間就熄掉的天空，是日夜循環最常見的破綻。

### 環境光變成 uniform，是被夜晚逼的

它原本是三個寫死的數字，在行進器、貓和植物裡各抄一份。有了夜晚之後它變成 uniform，因為**太陽下山之後它是唯一還在送光的項**：這裡的地面反照率大約 4%，方向項又被月光縮放過，環境光留在白天的值的話整片草原會解析成全黑，畫面就只剩一片星空加一個星團。

而夜晚的環境光**不是白天的縮小版**。縮小版正是讓夜景讀起來像曝光不足的白天的原因：夜裡的天空**相對於剩下的東西**比白天更藍，因為此刻唯一在照亮地面的就是天空自己。通道之間的比例才是全部的差別，絕對值幾乎不重要。

同一個 uniform 也正好是雪需要的東西 —— 見下。

## 雪，第二次

第一版拍出來是**沙丘**。

雪之所以亮是因為它**被照亮**，不是因為它的 albedo 接近 1。這個場景的太陽是琥珀色、tonemap 又大方，照實際亮度寫下去的雪出管線之後是奶油色。

第一次修的是 albedo：從 0.78 壓到 0.34，換回了明暗漸層（遠山開始讀得對），但近處平地仍然接近削頂。**真正缺的那一項是天光。**

雪的背光面幾乎完全靠天空在照亮。留在草原自己的環境光上，它就是一片沒有藍的蒼白表面 —— 那是沙。有了 `uAmbient`，答案是一行：

```glsl
vec3 fill = uAmbient * mix(1.0, 3.4, snow);
```

受光面暖（琥珀太陽）、背光面藍（天空），而那個對比才是眼睛在叫某個東西「雪」而不是「沙」時真正在讀的。

`snowCover` 的結果從 `material()` 用 out 參數回報而不是讓呼叫端重算：著色也要用它，而它是一次地形取值加三個正弦，不是那種為了一個已經在堆疊上的答案而每像素做兩遍的東西。

## 生物

貓以外，草原上活著的東西。目前兩種，而它們刻意被造在管線的兩端，因為它們是相反性質的東西：

**蝴蝶是一個物件。** 不透明、被照亮、草會擋在它前面、樹會遮蔭它 ——
所以它是幾何，和草畫進同一個目標、同一個深度緩衝，用同一份共用的植物標頭。**一隻四個三角形。**

**螢火蟲是一盞燈。** 在這個尺度下它沒有值得畫的身體；你看到的是光，
而光是加到影像上的東西，不是會擋住東西的表面。所以它畫在 tonemap 之後、加色混合，
躲在場景已經公布的深度後面，自己不寫任何深度。

兩者都沒有緩衝區、沒有屬性、沒有粒子記錄。每一隻都是自己索引的雜湊，
被時鐘推進、摺回一個跟著眼睛走的區塊 —— **把密度拉大就是 draw call 裡一個更大的數字，沒別的。**

### 牠們被允許待的地方

兩者都問地面**跟草一模一樣的問題**。湖上什麼都不會有 ——
一隻懸在開闊水面上一公尺的蝴蝶，是那種在它變成你唯一看得到的東西之前完全看不見的細節；
雪地上兩者都變少，因為那正是牠們所屬的草原正在做的事。

**這些是免費拿到的**，而那正是高度場和水位被做成單一答案、而不是每個 pass 各留一份的理由。

### 蝴蝶就是兩片翅膀

沒有身體、沒有觸角、沒有腳。在牠佔到的螢幕尺寸下 —— 最近時幾十個像素，任何誠實的距離下四五個 ——
身體只是兩翅之間的一團暗色，而翅膀在做全部的工作：
**讀起來像蝴蝶的是兩個面交替接住又失去陽光的那個閃爍**，而那正好就是兩片鉸在一起的四邊形給你的東西。

幾個跟著這個結論走的決定：

- **拍翅永遠不到水平。** 一片碰到水平的翅膀會在某一幀整面接住光而閃頻；壓在大約 20° 到 80° 之間 —— 那也正是真的蝴蝶絕大部分時間待的範圍。
- **高度是相對牠正下方的地**，不是相對牠的家。維持固定海拔的蝴蝶會在上坡時飛進山壁、在下坡時懸在半空。
- **航向直接來自路徑的導數**，所以牠永遠面向自己真正在去的方向。免費 —— 而另一個選擇（記住上一幀的位置）就是這整份檔案存在的目的所要避免的那個「每隻一份的緩衝區」。

### 牠去哪裡：真的那些花叢

蝴蝶飛向**花叢**，而且是花真的被播種在其上的**同一個叢格**（`clumps.js`，兩種語言一份）。

原本那個格子是 ground.js 的私事，直到有第二個東西想知道答案。搬出來的理由不是整潔：一個對著**自己另一份 scatter** 飛的蝴蝶，會在離花幾公尺的空草地上繞圈 —— 而**差一點比完全沒瞄準更糟**，因為眼睛立刻抓到那個落差，卻永遠不會注意到「沒有」。

搬家的代價寫在檔案裡：`seed` 在 JS 走 double、在 GLSL 走 uint，位元相同，只有最後那次除法差在第七位小數。這對一件事有影響 —— 一個雜湊值落在密度門檻千萬分之一以內的格子，可能被一邊判定有叢、另一邊沒有，症狀是一隻蝴蝶繞著空氣飛。一千萬格出一個，而修它的代價是往後永遠在兩邊扛一個整數比較。所以是**寫下來**而不是修掉。

花關掉、或那塊地本來就空的時候，牠退回自己的家點隨便晃。那不是 fallback 而是誠實的答案：沒有東西可以拜訪。

### 打斷圓的是離開，不是繞得不規則

第一版把相位調變、把半徑呼吸，然後每一隻**永遠鎖在同一叢上而且永遠不離開**。拓撲上還是一個軌道，而**一個封閉路徑無論被走得多不規則，眼睛半分鐘內就會找到它** —— 密度一高，整片就是一堆靜止的環。

真正打斷圓的是**離開**。所以時間被切成**段**：盤旋幾秒、竄到另一叢、再盤旋。

實作上只有一句話：**滑動軌道的圓心**，不去混合兩條完成的路徑。

```
target  = mix(fromC, toC, ease)
dTarget = (toC - fromC) * dEase
```

轉場於是免費掉出來：牠在行進中仍然在轉，速度是軌道的加上圓心的，而航向（就是導數）自己會傾進穿越、再傾出來 —— **不需要為衝刺本身寫任何東西**。

每一段用自己的段號當雜湊鹽從家附近九格裡挑一叢，所以鄰居不會全擠在同一朵花上，也沒有誰一輩子待在同一朵。`pickClump` 刻意**不是**「最近的一叢」：最近只是位置的函數，站在同一點的東西會挑到同一叢而且永遠挑它 —— 那正是「一堆靜止的環」的成因。

### 衝刺多久，由距離決定

固定的衝刺秒數表示速度是「間距除以它」。這裡的間距可以到八公尺，除以第一版的一秒半就是**每秒十二公尺**。那是鳥。

```glsl
const float CRUISE = 1.05;                       // 蝴蝶在花與花之間的實速
float legDash = clamp(crossing / CRUISE, 0.8, legSpan * 0.7);
float legDwell = legSpan - legDash;
```

段長固定、切分推導出來 —— 順序有意義：穿越要夠長才配得上距離，而距離要等段號挑完兩叢才知道，所以段長不能依賴它，否則兩個定義互相追。

smoothstep 的峰值是平均的 1.5 倍，所以**任何距離的最快瞬間都在 1.5 × CRUISE 附近**，不會因為格子怎麼排而失控。

實測（把公式轉寫成 JS 密集取樣 400 隻）：**盤旋最快 1.52、衝刺最快 1.87、合計最快 2.33 m/s，中位數 0.36、p90 1.55。** 中位數是一隻在花上懸停的蝴蝶，p90 是巡航，最大值是一次衝刺 —— 都在真實粉蝶的範圍內。

### 一個混單位的錯

脈衝的形狀是**踢擊週期**的函數，而 `dTarget` 是**對秒取的**（段的計時用真實秒）。兩者直接相加不是那種會在洗牌中抵銷掉的比例錯誤 —— 那是**兩個不同單位的向量在相加**，所以只要兩項同時活著，**方向就是錯的**。而兩項同時活著的時刻正是穿越，也正是航向唯一重要的時刻。

```glsl
dOff += d * (amp * ds * kickRate);        // 換算進「每秒」
...
vec2 vel = dOff.xz + dTarget;
```

這個錯在上一版就犯過（那時是 `dr`/`dphase` 對 `t` 取導數卻直接加 `dTarget`），改寫成脈衝列時原樣搬了過來，第二次才抓到。

### 這裡沒有軌道：脈衝列

前面兩版都是用**正弦**堆出來的，而正弦沒有讓蝴蝶認得出來的那兩個特徵：**沒有轉角，而且在時間上對稱**。

調變相位只改變那條曲線**被走的快慢**，改變不了它是一條曲線。而一條封閉路徑無論被走得多不規則，眼睛半分鐘內就會找到它 —— 在上面疊多少晃動都沒用，**因為晃動也是平滑的**。（那一版的晃動甚至還錯得跟直覺相反：固定振幅在懸停時是大偏離、在高速時是細嗡嗡，而細嗡嗡正是最需要幫忙的情況，因為一道又快又乾淨的弧沒有東西在遮它。）

動物真正在做的是：**踢一下、滑行、再踢一下。** 所以位移被寫成最近幾次踢擊的響應之和：

```
s(a)  = a * (1 - a/L)^2        a = 這一擊落下之後過了幾個踢擊週期
s'(a) = (1 - a/L)(1 - 3a/L)
```

`s(0) = 0` 而 `s'(0) = 1` —— **踢擊落下的瞬間速度就跳起來，那個不連續就是轉角本身**，而且它不用花錢，因為那正是這個算式本來就會做的事。`s(L) = s'(L) = 0`，所以一擊離開視窗時早已衰減到零，掉出去不會有 pop。

**有限記憶是它還能是封閉式的原因。** 真正的脈衝響應永遠不會真的到零，要加總就得記得這隻動物踢過的每一下；強制它在 L 歸零把迴圈綁在四次，這才讓一隻蝴蝶仍然只是「自己的索引和時鐘」的函數，任何地方都不需要緩衝區。

**同一列脈衝同時產生兩種行為**：在花上工作時方向是散的，穿越時方向偏向目標。所以長距離移動讀起來是**一串衝刺**而不是一次滑行 —— 沒有第二套機制負責旅行。

高度也出自同一列：每一擊都有垂直分量，所以牠被往上拋和被往旁邊拋是**同一個節奏**，這是任何一條獨立的高度波都做不對的事。

傾側改成**滾進剛落下的那一擊**，而不是滾進某種曲率。路徑由脈衝組成，本來就沒有平滑曲率可讀 —— 而且踢擊本來就是比較好的量：蝴蝶幾乎全是翅膀沒有質量，牠可見的動作是把自己往旁邊甩時**翻過去**，不是在轉角裡慢慢傾。

### 銳利度和速度是兩個旋鈕，只有一個是壞的

一擊的峰值**速度**是它的振幅乘以踢擊率，所以把振幅綁在花叢半徑上，一叢寬的花就會把動物以每秒好幾公尺甩來甩去。實測未設上限的版本峰值是 **6.4 m/s**，那是鳥。

加上限並放緩之後：

| | 速度 m/s | 轉向 rad/s |
|---|---|---|
| 未設限 | p50 0.94 · p90 2.08 · p99 3.35 · max 6.38 | p90 12 · p99 112 |
| **現行** | **p50 0.45 · p90 1.41 · p99 2.00 · max 3.12** | **p90 8 · p99 101** |
| 再放緩 | p50 0.33 · p90 1.41 · p99 1.84 | p90 5 · p99 76 |

**速度掉了一半以上，轉向的銳利度幾乎沒動**（112 → 101）。這就是分開調這兩件事的全部意義：**銳利度活在「起始」裡，速度活在「振幅」裡**，而只有其中一個是壞的。再放緩一級就開始把轉折磨平了，所以停在這裡。

### 一個沒預料到的代價

把飛行瞄準花之後，蝴蝶到了 —— 然後停在**恰好是花的高度**、混在一堆花大小花顏色的東西裡，於是**完全不再讀起來像蝴蝶了**。

在這個距離下，把動物和牠正在拜訪的植物分開的是：牠在植物**上面**。懸停高度的底從 16 公分抬到 30 公分。

### 麻雀：第一個矇混不過去的

蝴蝶是兩片翅膀，因為在這個場景會看到牠的任何距離下，**蝴蝶就是兩片翅膀**。鳥不是。

在看得清一根羽毛之前就能認出一隻小雀的是**輪廓**：三分之一處最寬的胸、比胸小而且沒有脖子接上去的頭、後面一條長尾。三個裡錯一個就是卡通，而且出錯的方式永遠是同一個 —— **頭太大**。

所以身體不是被畫出來的，是一張從真麻雀量下來的**環表**：沿身體多遠、多寬、中線抬多高。最要緊的那個數字是頭冠半徑除以胸半徑：

| | 頭／胸 |
|---|---|
| 這裡 | **0.64** |
| 真麻雀 | 約 0.65 |
| 童書插圖 | ≥ 1.0 |

沒有輪廓函式可以調，因為沒有東西要調 —— **頂點直接坐在量測值上**。

第一版用高斯疊加去逼近那條輪廓，頭胸比壓不下 0.87 —— 兩個高斯互相滲透，頭的那一團被胸撐大。把控制點**直接當成環**之後就精確命中了，而且更便宜。

### 唯一一個不是真實的量測

**身長刻意做成真麻雀的 1.5 倍**（13.5 cm，真的是 9），而理由不在鳥身上，在幀上。

真麻雀通勤時跑 6～9.5 m/s。九公分的身體、60 Hz，那是**每幀移動 10～16 公分 —— 超過牠自己一個身長**。任何每幀位移大於自身長度的東西都無法被解析，而這還沒算到時間累積濾波器接下來會把牠抹成一道條紋。

放大並同時減速之後：

| | 每幀位移（身長） |
|---|---|
| 9 cm、6–9.5 m/s | **1.11 – 1.76** |
| 13.5 cm、3–4.8 m/s | **0.37 – 0.59** |

**這個數字決定的是「畫面上有一隻鳥」還是「有一道條紋」。**

比例完全沒動 —— 這是把環表整個縮放，不是重新塑形，所以頭仍然是胸的 0.64，牠仍然是麻雀而不是麻雀形狀的鴿子。尺寸：頭 3.8 cm 寬、胸 6.0、翼展 30、尾 7.4。

減速本身也站得住：9 m/s 是橫越開闊地的速度，而在草叢之間移動慢得多，這片草原是後者。

而且它**沒被要求就順便修好了起伏飛行**：原本每個弧橫跨 4～7.5 公尺，真鳥是 2～3；減半之後是 2～3.8。**拍擊節奏一直都是對的，是速度在拖著它跑。**

### 起伏飛行，以及群

麻雀不走平飛。牠成串地拍幾下、然後收翅滑降，所以路徑是一連串淺弧，**每一次拍都在爬升、每一次停都在下墜**。那個起伏是遠到看不清翅膀時唯一的辨識特徵，而它只是一條正弦 —— 但必須是翅膀正在收合的**同一條**，否則就是一隻收著翅膀在爬升的鳥。

第一版把二十六隻平均撒在六十公尺的盒子裡，那是每一百四十平方公尺一隻，而一隻九公分的鳥在那個距離下不到一個像素。**牠們確實在被畫，只是不在那裡。**

麻雀本來就群居，所以改成**撒的是群、再把成員撒進群裡**。一個改動同時解決兩件事：這是動物真正在做的事，而且它把六七隻放在同一個地方，那是這個尺寸下眼睛唯一抓得到的排列。群的雜湊決定它在哪、往哪飛，所以整群一起通勤；每隻保留自己的拍翅相位和高度，所以它是一群而不是一個編隊。

### 「像一堆雜亂蒼蠅」的原因不是數量

第一版是**很多小群、撒得很開、每隻鳥照自己的時鐘拍**。那不是一個人手不足的鳥群，那是蟲群 —— 而原因不在數量。

鳥群之所以讀起來是鳥群，是因為**整群一起起伏、一起轉向**。而那一版每一隻的起伏節奏 `boundRate` 和相位都是從**自己的索引**雜湊出來的，所以七隻各自上下擺。加再多也只會變成更大的一團蟲。

所以節奏、航向和作息全部移到**群**層級，每隻只留 ±0.6 弧度的相位偏移 —— 夠讓牠們不是一排合唱團，遠遠不足以把群拆成個體。

隊形也從球改成**沿航向拉長**（縱橫比 3:1）：一群小鳥是長條的，而那個形狀讓群在鳥本身只有四個像素時仍然說得出方向。

控制改成調**群內數量**；群數是 3～6，而且**不是控制** —— 超過半打，眼睛就不再數「群」而退回看見一片散點，那正是這整套安排要修的東西。三群一定在，其餘三個各擲一次硬幣。群與群大小也不同，因為現實如此。

`--interact` 守著這一條：密度 0.35 給 20 隻、密度 1 給 60 隻，而**群數不動**。一支會加群而不是加成員的滑桿，正是讓滿天的鳥退回一片蒼蠅的那支。

### 一支視距，三個尺度

蝴蝶、螢火蟲、麻雀各自需要不同的可見距離，但那是**同一個量的三個範圍**，不是三個獨立的問題——所以是一支主控帶三個比例與上限，跟「植被視距」帶草/花/樹一模一樣：

| | 比例 | 上限 | 為什麼是這個上限 |
|---|---|---|---|
| 蝴蝶 | 0.50 | 30 | 七公分的東西，再遠就是把 instance 花在不到一個像素上 |
| 螢火蟲 | 0.80 | 55 | 它是一盞燈，傳得比身體遠 |
| 麻雀 | 1.60 | 130 | 三者中最大、飛得最高 |

**密度是密度，所以數量跟著面積走。** 固定數量而把視距拉遠，真正在做的事情是把族群變稀 —— 而「密度」和「視距」是兩支不同滑桿的全部理由就是它們回答不同的問題。

**麻雀是例外，而且是被當成例外守著的**：那裡的單位是**群**，所以拉寬視距是把群與群拉開，不是多生出鳥。`--interact` 兩項守這件事：15u → 120u 讓蝴蝶從 29 長到 405、螢火蟲 32 → 680，而**麻雀一直是 60 隻**。

### 不是一直在飛

麻雀一天有很大一部分不在飛。所以整群有一份作息：巡航 → 降落 → 停著 → 爬升離開。一個梯形，跨在群自己的週期上，**什麼都不用記住**。

停在哪是有趣的那一半：

**樹上** —— 用的是**真的樹冠、真的高度**，來自陰影圖本來就在畫的那份清單（`trees.perches()`）。另一個選擇是從植樹的雜湊在著色器裡重推位置 —— 那會得到正確的樹幹和**錯誤的樹冠高度**，因為一棵樹的高度來自它自己的生長流，不來自它的格子。

**地上** —— 沒有樹可停時就落地。而地上的鳥**會被貓趕走**，樹上的不會，那個差別就是「落地」這件事值得做的大半理由。

貓的位置**本來就是這支著色器的 uniform**，因為陰影需要它。所以這一整條行為的代價是一次距離計算：

```glsl
if (!inTree && uCatCaps > 0.5) {
  float away = length(uCatBound.xz - perchXZ);
  land *= smoothstep(2.6, 5.2, away);
}
```

不是開關。抬升攤在貓接近的兩公尺半上 —— 以走路的貓來說遠低於一秒，**讀起來是立刻，而且不可能爆掉**。

### 兩個實機回報的 bug

都不是參數問題，而且原因不同。

**轉鏡頭時整群消失。** 群被摺進一個**跟著鏡頭走的盒子**。這是軌道鏡頭，拉 yaw 會平移眼睛，摺法跟著變 —— 靠近盒緣的整群被淡出殺掉再從對面出現。幾百隻蟲看不出來；**只有四群時，一整群眨掉是畫面上最顯眼的事。**

改成跟草、花叢、樹 chunk 一樣的**世界格子**。群現在是因為跑出範圍而離開畫面，那是霧要做的事。

但一個 3×3 的視窗把同一個 bug 往外推了一層：眼睛跨格時視窗整個位移一格，還看得見的邊緣群照樣眨。**修法是讓淡出在視窗保證的半徑內收完** —— (2k+1) 的視窗保證 k 格（眼睛可以在自己那格的任何位置），所以改成 5×5 並把淡出夾在兩格內。

**緩飛一陣後突然轉向衝走。** 停棲期間 `flying = home + dir * uTime * speed` **一直在前進**。休息五到七秒後那個點已經在十五到三十五公尺外，起飛的 blend 要在一秒半內補完 —— **每秒十到二十公尺，橫向。**

飛行沒錯，錯在它被要求去追一個它一直在無視的時鐘。改成**一個週期就是一趟完整行程**：停著、起飛、飛到下一個棲處、降落。前一趟結束在這一趟開始的地方，**沒有缺口要補**。

順帶修掉的第三件：讀數原本數的是「視窗裡有幾群」而不是「看得到幾隻」，所以它會在畫面沒動的時候跳 —— **一個比畫面還活潑的讀數，沒人能拿來檢查畫面。** 現在它套用著色器同一條淡出曲線。

`--interact` 守這一條：鏡頭轉一圈，30 → 29 → 31 → 32（振幅 3）。舊的 bug 是整群在滿亮度下被換掉，比這個寬容度大一個數量級。

### 第二輪：轉向就是平移

上面那一輪修完，實機回報**還是會消失**，而且**暫停時轉向也會** —— 那是關鍵線索：`uTime` 凍結了，唐一還在變的就是 `uCamPos`。

量出來兩個都是幫兇：

**棲處清單是以鏡頭排序的。** `uPerch` 是離相機最近的六棵樹冠，而程式用 `uPerch[hash * n]` 選樹。探測直接拍到它們互換：同一棵樹 `[12.1, 0.9, 4.3]` 在 yaw 0 是 slot 0、yaw 2.4 變 slot 1、yaw 4.8 掉出前兩格。**停在樹上的整群會跳到別棵樹。** 改成按**到 home 的世界距離**排名取前二，排序怎麼來都一樣。

**而主因是：軌道鏡頭的「轉向」就是「平移」。** 轉一圈不是眼睛原地旋轉，是眼睛被帶著繞一個圓 —— 距離 4.5 公尺時移動 9 公尺，20 公尺時移動 40。錯在格子錯在眼睛上，於是使用者以為只是在看一看，格子已經位移了好幾格。

**那個圓的圓心不會因為轉向而動。** 改錨在 `this.center`（鏡頭繞什麼轉，不是鏡頭在哪）之後，**轉向的代價恰好是零** —— 那也正是它看起來應該是的代價。

驗證：暫停後轉一整圈，**31 → 31 → 31 → 31**（之前是 29 → 27 → 29 → 34）。斷言現在要求**完全相等**。我先前寫的是寬容度版本，而那是錯的工具：**它讓只修一半的版本通過了**。

### 從天上拍改成從上往下拍

驗收截圖原本把鏡頭朝天。那有兩個問題：抓不抓得到鳥全靠運氣，而且**深色的鳥襯深色的天，對比本來就最差**。

改成從十三公尺高俯視，鳥襯著草地。同一群動物，同一份幾何，可讀性差了一個量級 —— 這是一個關於**在什麼背景前看**的問題，不是關於鳥做得夠不夠好的問題。

### 螢火蟲連翅膀都沒有

牠是一個點。

- **在莖之間，不在空中。** 頭部高度的螢火蟲是一顆星；膝蓋高度的螢火蟲是一隻蟲，因為前面的草不斷把牠切掉。
- **閃爍是正弦的高次方**，所以它大部分時間是暗的、偶爾非常亮 —— 佔空比才是訊號，只會脈動的螢火蟲讀起來像一顆壞掉的 LED。
- **但不會全暗。** 這個場景還沒有夜晚可以藏草原，一群九成時間全黑的族群看起來會像「幾隻蟲」而不是「一片」；所以留了一個底，其餘的以餘燼的形式在場。
- **兩公尺內維持固定角尺寸**，之外維持固定世界尺寸 —— 光在任何距離都是光，變的是有多少。

### 為什麼會有 `plantUniforms()`

蝴蝶被加進來的那一刻，「每種植物都需要的東西」變成了**三個 pass** 在讀同一份 GLSL 標頭 ——
而一份被三支著色器共用、值卻被打了三遍的標頭，是一份只在紙上共用的標頭。

它壞掉的方式不是 crash：是某一個 pass 悄悄留著上禮拜的漣漪半徑，
於是同一片草原上、星團底下的陰影會依照站在裡面的是什麼東西而有兩種邊緣。

所以那份 uniform 集合也搬進了 `plant.js`。呼叫端往上疊自己的 —— 額外的 key 不花錢，
著色器沒宣告的 uniform 上傳時會被跳過。

## 能見度：一個主控，一個從屬

霧原本是寫死的常數，而那個常數把地平線放在 **66 單位** —— 這就是世界感覺很小的原因。

現在「能見度」是滑桿（40–220 單位），它同時定霧的濃度**並寫入**「植被視距」：

```
uFog = 3 / (0.045 × 能見度)     // 讓 95% 濃度正好落在你要的距離
植被視距 := 能見度 × 0.9
```

寫入而不是讀取 —— 跟「總體品質」與它下面七項的關係一模一樣。動完主控之後，視距那支滑桿仍然是你的，主控只是變得過時。

### 為什麼不鎖成一條

兩個理由，都不是偷懶：

**同一個霧濃度需要的視距會隨鏡頭改變。** 貼地平視時地面到 60 公尺就沒了；把俯角拉高往下看，同樣的霧下地面能延伸到一百多公尺。一條鎖死的滑桿在某些角度露出草皮邊緣，在另一些角度浪費一半預算。

**兩者是不同性質的東西。** 霧是氛圍，視距是預算。鎖在一起就禁掉了「濃霧＋遠視距」這個又便宜又好看的組合。

真正的約束是**單向**的：視距 ≥ 霧關閉的距離，否則會看見世界的邊緣。主控只保證這個下限，不需要相等。

`--interact` 兩項守著它：拉到 180 會把視距寫成 162、五個環；接著手動把視距拉回 30，能見度仍然停在 180。

### 一個視距，三個消費者

草、花、樹**共用同一個視距**，各自帶自己的比例與上限：

| | 比例 | 上限 | 為什麼是這個上限 |
|---|---|---|---|
| 草 | 1.0 | 200 | 環數 `MAX_RINGS = 5` |
| 花 | 0.62 | 60 | 叢格固定 4 公尺，數量隨視距平方成長 |
| 樹 | 0.75 | 90 | 樹枝段**沒有 LOD**，再遠就填滿緩衝區 |

樹看得比花遠，因為樹是這裡唯一高到能構成天際線的東西 —— 遠處那道樹線就是「多遠」本身。

實測（能見度 180）：`grass 162u, flowers 60u, trees 90u`，`--interact` 有一項在守。

## 驗收工具：`tools/verify.mjs`

同樣零依賴。它用 Node 內建的 `WebSocket` 與 `fetch` 直接講 Chrome DevTools Protocol ——
沒有 puppeteer、沒有 playwright、沒有測試框架。協定就是 socket 上的 JSON，這就是全部的依賴表面。

```bash
node tools/verify.mjs                # 六種設定各載入、渲染、截圖，回報任何 console error
node tools/verify.mjs --interact     # 端對端互動驗收（真的去拖曳滑鼠、滾滾輪、按鍵）
node tools/verify.mjs --responsive   # 手機 / 平板 / 筆電 / 超寬視窗版面與像素預算
node tools/verify.mjs --bench        # 固定負載的效能量測，逐項拆解成本
node tools/verify.mjs --bench --gpu high   # 同上，但強制用獨顯
node tools/verify.mjs --diff         # 凍結時間、翻轉設定、逐像素量出「看不看得出來」
node tools/verify.mjs --head         # 開可見的瀏覽器視窗
node tools/verify.mjs --serve        # 只開靜態伺服器
node tools/verify.mjs --eval probe.js --at "#/march"   # 在頁面裡執行探針，檢查活的 GPU 狀態
```

截圖輸出在 `tools/shots/`。除了抓圖之外它還會斷言：畫布不是單一顏色（全黑代表沒渲染）、
`gl.getError()` 乾淨、沒有未捕捉的例外。

`--interact` 的 79 項檢查涵蓋：intro 關閉、**點擊真的擊中表面**、**留下漣漪**、
**漣漪被宿主帶著移動**、**點在天空不會有反應**（CPU 的挑選與螢幕上看到的一致）、
指標事件真的進到畫布、拖曳繞行鏡頭、滾輪縮放、XY 盤轉動光源、`Ctrl`+`K` 面板、模糊搜尋、
**主品質滑桿一次推動七項**、**個別滑桿仍能覆蓋主滑桿**、
渲染縮放真的重配了 render target、參數往返 URL、暫停真的停住時鐘、`.` 前進一幀、
禪模式、快捷鍵表、單場景時隱藏 tab bar、恢復預設值，以及全程零 console error。

還有一批是**截圖看不出來**的斷言，也正是為此才存在：

- **淹掉山谷會淹死長在裡面的東西**（4,816 朵花 / 44 棵樹 → 2,550 / 26），而**把湖關掉會一株不差地還回來**。第二項是這裡最重要的迴歸：每一支 include 地形區塊的著色器都宣告了 `uWaterY`，漏填一個上傳點就會讀到 0 —— 那是一座站在世界每一道稜線之上的湖，和一片什麼都不長的草原。
- **水位是線性於淹沒面積、不是線性於深度**（4,816 · 3,708 · 2,550）。`checkWater()` 從高度場那一端守同一件事；這一項從管線的另一端守。
- **雪會埋掉花，雨不會碰它們**（4,816 · 4,816 · 440）—— 一個被造成「一種強度」的天氣會讓兩個數字一起動。
- **雪帶走風積處、留下被掃過的地方**（440 朵還站著）。全有或全無代表 `snowCover` 的斑駁是平的。
- **每種生物有自己的控制**，以及**一隻蝴蝶四個三角形、一隻螢火蟲零個**（180 → 720；260 → 0）。這兩個數字就是這兩個東西各自的主張，不該只能靠相信。
- **時刻把太陽放在一道弧上，月亮放在同一道**（正午 y 0.92；07:30 和 16:30 同高、左右相反；午夜的月亮在正午太陽的方位）。
- **時刻接手之後，方向盤就不再被聽了** —— 在指定時刻下拖動方向盤，光源一動不動；切回固定，它立刻回來。一個在別的控制接手之後還會動光的控制是三種設計裡最糟的，因為畫面上沒有任何東西說明你正在看哪一種。
- **換天體的那一瞬間，光已經沒有東西可以給了**（18:00 時光源離地平線 `0.0000`）—— 這就是黃昏的方向翻轉看不見的原因。
- **暫停會停住太陽，繼續會讓它再走**。它被模擬時鐘推進而不是牆上時鐘，否則凍結的參考截圖就不可重現。

每次執行前還會先跑兩個毫秒級的檢查。一個是 lint：掃描所有著色器樣板字串裡有沒有反引號。
GLSL 註解裡的一個反引號會提前結束 JS 樣板字串，然後在五十行之外炸成一個
毫不相干的識別字錯誤 —— 這件事我踩了三次才決定寫成檢查（第四次是這輪加水的時候，它當場攔下來了）。

另一個是 `checkWater()`：拿另一個取樣格重新數一遍水面底下有多少地，確認**水位滑桿說的和地形實際的一致**。
截圖檢查不到這件事 —— 會壞掉的不是畫面而是「控制的意義」和「地面的形狀」之間的約定，
而它會在有人動了 `WAVES` 裡一個波長的那一刻壞掉，靜止畫面上看不出任何不對，湖只是不再是它宣稱的大小。

合成點擊不用眼睛瞄「畫面中間」，而是把球心投影成 CSS 座標再點下去 ——
用眼睛瞄的話夠常落在空無一物的天空，足以讓測試對它宣稱在檢查的功能說謊。

### 它抓到的八個真 bug

1. **`[hidden]` 被 CSS 打敗。** `.fallback { display: grid }` 的優先權高於 UA 對 `[hidden]` 的
   `display: none`，所以「需要 WebGL2」的錯誤畫面一直蓋在正常運作的網站上面。
2. **切換場景時 render target 停在 2×2。** 換場景不會改變畫布尺寸，所以 `_resize()` 的
   「有變化嗎？」提早 return，新場景永遠拿不到真正的解析度。
3. **`gl_PointSize < 1` 的粒子被硬體丟棄。** `ALIASED_POINT_SIZE_RANGE` 在這張 GPU 上從 1 開始，
   而透視除法把點的大小算到 0.29 —— 26 萬個粒子一個都沒畫出來。
4. **拖曳在開始的那一幀就被取消。** 用 `setPointerCapture` 之後又監聽 `pointerleave` 來結束拖曳
   是錯的：呼叫 capture 本身就會觸發一組 out/leave。
5. **場景上下顛倒。** `right` 算成了 `cross(worldUp, fwd)` 而不是 `cross(fwd, worldUp)`，
   負號穿過下一個外積傳給 `up` —— 格線地板一直畫在天空裡，而場景夠對稱，
   對稱到這件事看起來像是刻意的構圖。
6. **View Transition 被中斷時丟出未處理的 rejection。**
7. **靜態的 hint 區塊被當成有值的控制項註冊。** 它帶了 `id`，於是進了 state map，
   第一次程式化 `setValues()` 打到一個沒有 `set()` 的元素就爆掉。
8. **低幀率時點擊沒有反應。** 靠算繪迴圈取樣 `pointer.down` 來判斷點擊是錯的，
   25 fps 下一次快速點擊可以整個發生在兩幀之間 —— 要在 pointer 事件上判定。
   （這個修正留在 `core/pointer.js` 的 `onDown` / `onUp` 回呼裡，目前沒有人用。）

第 5 個特別值得一提：它是被截圖裡「格線出現在地平線上方」這個細節抓到的，
而不是被任何斷言抓到的 —— 這正是為什麼驗收工具要輸出可以用眼睛看的東西。

## 效能

`--bench` 跑固定負載（關掉鏡頭自轉與時間累積，兩者都會把成本藏進被抹掉的幀裡），
量最近 90 幀的中位數與 p95，再逐項拆解每個著色項的成本。
**讀 GPU ms 而不是 fps** —— 著色器一旦夠快，幀時間就會貼在合成器的節奏上，
每個案例都讀到同一個數字，那什麼也沒告訴你。

1600×900，全解析度的 GPU 時間：

| | Iris Xe | GTX 1650 |
|---|---|---|
| 優化前 | 42.5 ms | 22.9 ms |
| **優化後** | **9.0 ms** | **4.6 ms** |

程式端 4.7 倍、換獨顯 2 倍，合起來 **42.5 → 4.6 ms，約 9 倍**。畫面是同一張。

### 程式端做了什麼

**地板不再被 march。** 平面就用 `t = (FLOOR_Y − ro.y) / rd.y` 一步算完，
再和星團的結果比誰近。掠射射線本來會沿著地板把整個步數預算走完，什麼也沒換到。
（附帶修掉一個 bug：舊版地板會被步數預算截斷，所以格線的消失距離會隨「行進步數」滑桿改變。）

**星團有一個包圍球**，每幀在 JS 用擺放球體的同一組數字算出來（再加上 smin 的外凸、
擾動振幅、進行中的漣漪振幅）。著色器需要的每一個距離都從它推導：從哪裡開始 march、
何時放棄、陰影射線走到多遠還有意義。**著色器裡一個寫死的尺度都不剩**，
所以之後改場景大小不用重調六個常數。

包圍球還讓 march 從**進入點**開始，而不是從鏡頭前面慢慢逼近；沒打到包圍球的射線直接跳過。

**噪聲只在接近表面時算。** `snoise` 是整個著色器裡最貴的函數，原本每像素被呼叫約 264 次
（主射線、法線、陰影、AO，反射再一輪）—— 包括那些離表面還很遠、位移根本不可能影響結果的
取樣點。超出一個幾倍振幅寬的帶狀區時改回傳 `d − 振幅`，那是真實距離的合法下界，
追蹤器保持保守、不會穿透，而且完全跳過噪聲。

**場的三層。** `clusterBase`（球+環）→ `clusterShape`（+漣漪）→ `clusterFull`（+噪聲）。
陰影與 AO 用哪一層是個開關，因為那是判斷不是事實 —— 見下面的量測。

**背光面不打陰影射線。** `ndl <= 0` 時結果會被乘上 0，原本照樣跑 48 次場求值。

**距離場沒被擾動時，步長從 0.88 放回 0.97。** 0.88 是為了噪聲與漣漪才壓的。

### 品質旋鈕

七個旋鈕（渲染縮放、行進步數、陰影步數、遮蔽取樣、反射步數、陰影含表面擾動、
反射含陰影遮蔽），外加一個**總體品質**主滑桿：碰它就一次寫入全部七項。
主滑桿是一個**動作而不是綁定** —— 之後你仍可單獨微調任何一項，主滑桿只是變成過時的讀數。

`--diff` 凍結模擬時間、翻轉一個設定、重繪、逐像素比較，所以「這個看不出來」是量出來的
而不是講出來的。實測拐點（最大通道差歸零的位置）：

| 預算 | 拐點 | 預設 |
|---|---|---|
| 行進步數 | ~70 | 100 |
| 陰影步數 | 32 | 32 |
| 遮蔽取樣 | 5 | 5 |

品質曲線的中點就落在這些拐點上：往上是買鏡頭角度與參數組合的餘裕，往下才開始換掉看得見的東西。

兩個開關則**確實看得出差別**，只是範圍極小：關掉「陰影含表面擾動」有 0.16% 的像素
差超過 2 階、最大差 85；「反射含陰影遮蔽」是 0.19% 與最大 103。
兩者現在各只要約 1 ms，所以預設都開著 —— 預設畫面等同優化前，改變的是速度不是圖。

---

**Chrome 預設不會用獨顯。** WebGL context 上的 `powerPreference: 'high-performance'`
是頁面在瀏覽器**已經決定用哪張卡之後**才給的提示，它自己搬不動你。要真的切過去：

- **Windows 設定 → 系統 → 顯示器 → 圖形** → 加入 `chrome.exe` → 高效能，或
- **NVIDIA 控制面板 → 管理 3D 設定 → 程式設定** → Chrome → 高效能 NVIDIA 處理器

設好之後跑 `node tools/verify.mjs --bench`（**不加** `--gpu`），
它印出的 renderer 字串會直接告訴你成功了沒 —— 那個設定是綁執行檔路徑的，
所以驗收工具用的臨時 profile 也吃得到。
