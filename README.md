# AETHER — SDF 光線行進

一個完全跑在 GPU 上的場景。**零依賴、零建置、零打包器**：沒有 npm、沒有框架、沒有函式庫，
`index.html` 開起來就是全部。所有東西都是 `<canvas>`、原生 ES modules，與手寫 GLSL。

**距離場裡沒有任何一個頂點、沒有任何一個三角形。** 一道 fragment shader 沿著射線走進由距離函數
定義的隱式曲面：一團互相以 smooth-min 焊接的公轉球體，加上一個以自己的節奏翻滾的環。
陰影來自朝光源再走一次，環境遮蔽來自在命中點周圍取樣距離場，反射來自沿鏡射方向再走一次，
抗鋸齒來自每幀抖動取樣點再讓時間累積把它收斂掉。

**點擊星體或星環，被碰到的那一點會盪出漣漪** —— 表面凹出一個火山口，
一圈熾熱的環沿著表面擴散出去。把「質量消散」拉大，那一擊會把星環啃出一個缺口、
甚至把球體吃穿；能量排空之後兩者都長回來。

場景裡唯一由三角形構成的東西是**那隻貓**，用 `WASD` 驅動牠在地面上走動。牠不走同一條管線，
兩者在「深度」相接；星團會在牠身上投影，牠也會在地板上投影 ——
見〈[一隻光柵化的貓](#一隻光柵化的貓)〉。

## 點擊漣漪

點擊需要一個 shader 給不出來的答案：**游標底下是什麼？** 所以射線在 CPU 上再走一次，
對著同一組基本形體。也因此球體座標改由 JS 計算後上傳，而不是在 shader 裡從 `uTime` 推導 ——
一個現在有兩個讀者的場景，需要單一真相來源，兩份同樣的公式正是會悄悄走偏的那種東西。

CPU 的那次行進刻意**不含**表面擾動與漣漪：它們最多把表面推開兩公分，遠低於一次點擊需要的
精度，而納入它們會讓每次點擊都付一次噪聲函數的代價。法線用中央差分取六個樣本 ——
一次點擊跑一次，不是一個像素跑一次。

撞擊由三件事構成：

**凹陷與波。** 加在**距離場本身**上的一項。沒有網格可以推，所以波不是被畫上去的，
**波就是表面**。這一項的梯度會隨振幅與波數線性上升，所以行進步長是**從它們推導**的，
不是猜一個常數：把深度調高，追蹤器會變慢，而不是穿過表面。
（預設值算出來剛好是 0.88 —— 也就是這個機制取代掉的那個寫死的數字。）

**質量消散。** 波只能把表面推開一點點，再深就不再是距離場了。要真的少掉材料，
最直覺的做法是布林減去一顆球 —— 精確、便宜，但它留下一道**車床切出來的圓形邊緣**，
那不是任何能量真的會造成的斷面。

所以這裡用的是**加法**：能量高的地方把表面往內推，邊緣是平滑收細而不是被切開。
消散量超過當地厚度的地方，表面就直接不存在了 —— 星環只有 0.075 厚，
所以那裡會裂開一個缺口。

**癒合時收縮的是受損區域的半徑，不是深度。** 讓深度均勻淡出是直覺的做法，而且是錯的：
任何小到整個落在受損範圍裡的東西，會先縮小、再從自己的正中央長回來。改成收縮邊界之後，
最外圈的材料先回來、中心是最後閉合的那一點 —— 那才是一個洞真正癒合的樣子。

**波在受損區內被靜音。** 行進中的正弦有負相位，而負相位會把表面往**外**推 ——
不處理的話，缺口會在中央長出一小塊材料，跟著波前一路帶到邊緣。
已經消散掉的東西，沒有介質可以承載波。

加法還有一個好處：它的梯度是「振幅除以邊緣寬度」而不是「振幅乘以波數」，
而那個邊緣寬度是固定的，所以它直接吃前面那套「步長從場扭曲推導」的機制，
不需要任何特例，也不會因為撞擊處在生命週期的哪個階段而改變成本。

這一項放在**形狀層**而不是完整層：缺口對陰影與遮蔽射線也必須是缺口，
否則你會看到光拒絕穿過一個明明看得穿的東西。

**衝擊環。** 單靠幾何位移，在一個平滑的奶油色曲面上就是「技術上正確、但幾乎看不見」。
所以波前另外帶一圈**發光**——那是 emission 不是幾何，不花任何距離場穩定性的代價，
而且一眼就讀得到。

漣漪的圓心每幀從它撞上的東西重新算，不是撞擊當下烙在世界座標上：球體在公轉**而且會脈動**，
所以存的是一個**方向**、每幀重新貼回表面；星環則存環座標系裡的點再轉回來。
（驗收工具會檢查這件事：漣漪中心在半秒內確實被宿主帶著移動了。）

**點擊與拖曳**靠按下到放開之間指標移動了多遠來區分 —— 而且是在**事件**上判定，
不是在算繪迴圈裡取樣：25 fps 的場景上，一次快速點擊可能整個發生在兩幀之間。

## 值得一看的幾個決定

**Uniform 反射。** GPU 在連結程式時就已經知道每個 uniform 的名字、型別與位置，所以要求作者
在 JS 裡再抄一遍純粹是重複。[`core/program.js`](src/core/program.js) 讀一次反射資料，
之後 `prog.use({ ... })` 依型別自動分派到正確的 `gl.uniform*`，並把材質綁到自動指派的
texture unit。整個專案沒有一行 `getUniformLocation`。

**沒有建置步驟，所以 GLSL 就是 JS 模組。** 沒有 `#include`，共用著色器碼就放在
[`shaders/common.js`](src/shaders/common.js) 的字串常數裡用 `${}` 組合。這不是妥協 ——
它意味著著色器由瀏覽器自己的模組圖管理，沒有前處理器需要除錯。代價是：GLSL 註解裡不能有反引號，
不然樣板字串會提前結束（這件事花了一次 boot failure 才學會）。

**一個超大三角形，不是兩個。** 覆蓋全螢幕用 `(-1,-1) (3,-1) (-1,3)`：沒有對角接縫、少一個頂點，
而且 GPU 不會在斜邊重複光柵化同一個 pixel。

**Ping-pong 是型別的一部分。** `DoubleTarget` 把 `.read` / `.write` / `.swap()` 包在一個物件裡，
消滅了最常見的 bug：忘記自己在哪一半。時間累積就是靠它 —— 對著同時是當前 colour attachment
的材質取樣是未定義行為，而它產生的瑕疵看起來夠合理，合理到可以浪費你一個晚上。

**免費的抗鋸齒。** 每個 pixel 每幀把射線方向抖動不到一個 pixel，再讓時間累積把這些樣本平均掉。
鏡頭移動時混合係數自動調低，否則抖動會變成拖影。

**參數即 URL。** `#/march?balls=9&blend=0.55` 是你眼前畫面的完整描述。拖曳 slider 時用
`replaceState` 寫回位址列 —— 值得分享的狀態就是能寄給別人的狀態。驗收工具也靠這個擺場景。

**自訂元素包住原生控制項。** 每個 widget 底下都是真正的 `<input type=range>` /
`<button role=switch>`，只有像素是我們的。鍵盤操作、螢幕閱讀器語意、IME 行為全部來自平台。

**時間分兩種。** `clock.dt` 是模擬時間（可暫停、可縮放），`clock.wallDt` 是真實時間（永不為 0）。
暫停場景不會讓 UI 動畫卡住；一個異常長的幀（切回分頁、著色器重編譯）永遠不會被交給
積分器 —— dt 上限鎖在 1/20 秒。

## 一隻光柵化的貓

貓是一份程序化模型：~40 顆球體／管狀體，經過二次塑型、頂點染色、反殼描邊，
原始碼在 [tools/cat-model.js](tools/cat-model.js)。它**不 import three，THREE 由呼叫端傳入**，
所以能在 Node 裡跑 —— 我們跑它一次，把 three 丟掉，留下頂點。

模型與它需要的 three 都**放在本專案的 `tools/` 裡**，烘焙不讀取這個 repo 以外的任何東西。
`tools/` 是冷路徑：不會被 serve、不會被打包、app 不會 import 它 —— app 本身依然零依賴。
保留三個花色（橘白／虎斑／三花），其餘沒有帶進來。

### 兩條管線在哪裡相接

不是在幾何上，是在**深度**上。這個場景本來就已經把深度公開了：march pass 把射線走過的距離
寫進 colour target 的 alpha，好讓撞擊閃光能躲在幾何後面（`outColor.a = mat > 0.5 ? t : 1e4`）。

貓寫同一個量 —— `length(world - camera)`，同樣的單位 —— 進自己 target 的 alpha。
於是合成就只是每個 pixel 一次比較，寫在時間累積那一遍裡：

```glsl
vec4 scene = texture(uSrc, vUv);
vec4 mesh  = texture(uMesh, vUv);
if (mesh.a < scene.a) col = mesh.rgb;
```

（後來草地也走這條路，所以那張 target 叫 `meshRT` 而不是 `catRT`：貓和草**共用同一個
depth buffer**，這就是為什麼貓是站「在草裡」而不是站在草的圖片上。）

畫布上**依然沒有 depth buffer**（`depth: false` 沒有動過）。貓自己的 target 掛了一個私有的
depth renderbuffer，那只是為了讓牠自己的三角形彼此排序。march 完全不知道貓存在。

投影矩陣不是另外建的，是從 march 用的同一組 `uRight/uUp/uFwd/uFocal` 反推出來的 ——
沒有第二份相機資料可以走偏。

### 兩種操作方式（按 `Y` 切換）

| | 轉向 | WASD 的座標系 |
|---|---|---|
| **依鏡頭方向**（預設） | WASD 指哪就轉去哪 | **畫面**：`W` 遠離你、`S` 朝向你 |
| **滑鼠轉向** | 滑鼠滑動，不用按鍵 | **身體**：`W`／`S` 沿鼻尖，`A`／`D` 左右平移 |

模式名字說的就是「WASD 是用哪個座標系表達的」，差別全部在這裡。

預設模式下貓**永遠只往前走** —— 沒有倒退、沒有側移，因為動物是轉過身再走的。
按 `S`，牠會轉過來朝你走過來。速度會依「身體已經多接近目標方向」縮放（有下限）：
沒有這個縮放，貓每次掉頭都在甩尾漂移；沒有下限，牠每個轉角都會停死。

只有滑鼠轉向模式能讓貓往「牠沒有面向的方向」移動。

**一個必須成對處理的陷阱**：WASD 既然是用鏡頭的座標系表達，跟隨鏡頭就**不能**追著貓的朝向轉。
否則按住 `S`：貓轉過來面向你 → 鏡頭繞到牠身後 → 「朝向你」現在指向別的地方 → 牠再轉一次 ——
原地無限打轉。所以依鏡頭方向模式下，跟隨鏡頭**只追位置，朝向留給使用者拖曳**；
只有滑鼠轉向模式才把鏡頭釘在貓身後。

**指標鎖定**是讓滑鼠轉向真的可用的關鍵：沒有它，游標會撞到螢幕邊緣，轉一半就轉不下去了。
鎖定在按下 `Y` 的那一刻請求 —— 按鍵正好是瀏覽器要求的 user gesture。

但它**不是必要的**。如果鎖定被拒絕（嵌入式或自動化的文件可能根本不被允許），或使用者按 `Esc`
放掉了，這個模式仍然能用 app 本來就在累積的 pointer delta 運作 —— 只是會用完桌面空間。
點畫布可以重新鎖定。降級成堪用，比整個模式拒絕運作好。

被拒絕是常態而非例外，所以那個 promise rejection 是被吞掉的 —— 放著不管會浮出成
unhandled rejection，看起來像故障，但它不是。

兩個順帶的後果：
- 滑鼠已經有工作了，所以**滑鼠轉向模式下拖曳不再繞行鏡頭** —— 否則兩者會搶同一個位移。
- 指標被鎖定時沒有游標位置可以瞄準，所以**點擊改成打畫面正中央**。反正十字準星本來就是這樣，
  漣漪在滑鼠轉向模式下照常能打。

跟隨鏡頭在這個模式下是**直接釘在 `catYaw + π`**、不做緩動：滑鼠就是鏡頭，任何延遲都會讀成畫面卡住。

### 眼部雷射：對星體的動能

在**跟隨貓的鏡頭**下按左鍵，從貓的雙眼射出兩道紅色雷射，一路打穿星體與星環。
鏡頭鎖定在星團上時不會開火 —— 那個模式是在**看**它，不是在**當**牠，點擊仍然是打在表面上。

瞄準方式看**指標有沒有被鎖定**：

| | 瞄準 | 扳機 |
|---|---|---|
| 已鎖定（滑鼠轉向） | 準心，也就是鏡頭前方 | **按住連發**（0.13 秒一發） |
| 未鎖定 | 游標指到的那個點 | 一次點擊一發，**點空不發射** |

未鎖定時貓會**先轉身面向目標再射**，光束是「貓眼 → 目標點」的連線，不是鏡頭的方向 ——
除非你正好站在牠正後方，否則那是兩個看得出差別的方向。

### 頭先轉，身體才跟

看東西的是頭，不是身體。所以瞄準時**脖子先轉**，肩膀只補它轉不完的部分 ——
再加一點點，因為完全不動肩膀的貓會變成貓頭鷹。脖子的範圍是 ±0.9 弧度（約 52°），
超出的部分才交給身體；範圍內身體也只跟轉 25%。

頭同時會**依光束的仰角俯仰**。頭骨的正 X 是「鼻子朝下」，所以往上瞄是負值 ——
這在兩種模式下都成立，任何一發射擊都會把頭轉到槍管的方向上去。

身體的分配是在**排定射擊的當下算好一次**，不是每幀重算。這裡踩過一個坑：
一邊每幀重算「還差多少的 25%」、一邊又用「剩餘時間的比例」去緩動，
身體會反覆追著遞減的餘量跑，最後轉的量遠超過它該分到的。
固定距離、按剩餘時間比例前進，才會剛好在延遲結束時到位。

瞄準的權重是**快進慢出**：射擊在轉身結束的那一刻發生，頭還在追的話就等於沒瞄；
放開之後才慢慢飄回步態。

**點到空處不發射。** 未鎖定時「點擊就是瞄準」，所以點在空處等於沒瞄任何東西 ——
為一次手滑花掉一發並不合理。鎖定時沒有這種情況：準心永遠指著某個地方。

轉身**最多**需要 0.15 秒，射擊因此有延遲。那個延遲**不是要被壓低的成本**：
光束若在動物還沒看過去之前就射出來，讀起來像瞄歪了，而不像反射動作。

但延遲是**那個轉身**，不是一筆過路費：已經在看著目標的貓沒有頭要轉，
所以延遲按「實際要轉多少」縮放。否則對著正盯著的目標連發會一直卡頓。

指標被鎖定時不用等 —— 那時貓本來就正對著準心。

扳機是**狀態轉換**不是事件：pointer 層可能把同一次按壓回報兩次（它會自我修復
「第一個 move 事件就已經按著」的漏接），以按下本身上膛會一次射兩發。

未鎖定時滑鼠還要負責繞行鏡頭，所以那裡是「沒有拖曳的點擊才算一發」；鎖定時滑鼠沒有別的工作，
才能按住連發。

**畫的，不是行進出來的。** 一道雷射只有幾公釐寬而且完全筆直 —— 那是 sphere tracer 最不擅長的
形狀，每條射不中的射線還是得付出代價。當成兩片面片就只是 12 個頂點。

畫兩道是因為有兩隻眼睛，但**物理只用中間一條軸**：兩眼在一隻一公尺高的動物上只差幾公分，
沒有任何值得計算的衝量分得出來。

遮蔽是白拿的：讀場景那條深度 alpha（撞擊閃光用的同一條），所以有東西擋在前面時光束會被切掉。

但**光是深度測試不夠**：它只會把「有東西更近」的地方藏起來，那不等於讓光束停下。
穿過球體的光束會在球內被正確藏住，然後從另一側**冒出來繼續射向天空** ——
那讀起來像從星團後面經過，而不是打中它。所以射程是開火時用 CPU 走一次同一個場量出來的
（地板是平面，直接解交點）。

### 兩個非顯而易見的坑

**不能用世界空間的 billboard。** 直覺做法是 `cross(光束方向, 朝向眼睛)` —— 在這裡剛好完全錯誤：
雷射是**沿著準心**射出去的，所以它幾乎與視線平行，那個外積會塌成零，面片寬度變成 0、整道雷射看不見。
改成沿**投影後**的光束方向取垂直，就沒有退化情形，而且得到固定像素寬度 —— 雷射本來就長那樣。

**一次按壓只能是一發。** pointer 層可能把同一次按壓回報兩次（它會自我修復「第一個 move 事件
就已經按著」的漏接情形，而合成事件也會兩者都送），所以以「按下」本身當扳機會一次射兩發。
扳機是那個**狀態轉換**，不是那個事件。

### 漣漪的中心從點變成線

一次點擊留下的是**點**衝擊，波以球面從那一點盪開。一發雷射留下的是**線段** ——
它穿過的整段距離 —— 同一個波就以**圓柱面**從那條線盪開，於是打開的是一條貫穿的通道，
而不是一個「它剛好先碰到哪裡」的坑。

衝擊從一個點變成一個**線段**。長度為零的線段就是點，clamp 會自動處理，所以質量消散那一段
點擊和雷射走的是完全同一段程式碼。

**但波的方向要分開。** 一開始兩者都用「點到線段的距離」當波前，結果雷射會從光束**側面**
把波徑向甩出去 —— 那是點衝擊的行為，而光束不往旁邊推任何東西，看起來就是錯的。
所以貫穿的波前改成沿**軸向**量，在生命週期內從入口掃到出口，再加一個徑向衰減把它關在
自己鑽出來的洞裡。點衝擊維持球面擴張不變。

**消散強度也分開。** 一次點擊是凹陷，一道雷射必須貫穿 —— 洞得比它要穿過的壁還深。
強度存在線段另一端那個沒用到的分量裡（`uRippleTo[i].w`），點擊是 1、雷射是 4。
消散量因此**不再夾在 1**：夾住的只有「用來讓波靜音的遮罩」，深度是原始值，
而那正是「打穿一顆球」和「在上面壓一個凹痕」的差別。

追蹤器的步長上限是從消散的梯度推導的，所以那個 4 倍也得餵進去 ——
但是**用當下真正存在的最大強度**，不是編譯期常數：否則每一次普通點擊都要用雷射的步伐前進，
白白慢一倍。

線段是「光束被星團包圍球裁切後的那一段」，也就是它唯一可能在任何東西裡面的那一段。
它**釘在世界座標**上，不像點擊那樣掛在某顆球上跟著公轉：貫穿的通道穿過的是「當時擋在路上的東西」，
沒有哪一顆球擁有它。

雷射因此**不會停在第一個表面**。它會穿過去、從另一側出來，而它鑽開的通道正是讓你看見它穿過去的東西。
唯一會終止它的是地板，那是一個平面，直接解交點。

### 柔軟的尾巴

尾巴不是棍子。牠被身體帶著走，而且**越靠近尾梢的點，越晚才知道身體動了**。

做法是一條彈簧鏈：9 個節點，每一節被更靠近尾根的那一節拉著。這個拉力是**單向**的 ——
後面的節點永遠不會反過來拖前面的，所以身體主導、尾巴跟隨，而不是兩者互相拉扯。
延遲沿著鏈累積，柔軟感就是這樣長出來的，沒有人手寫過一條延遲曲線。

原模型每幀在 CPU 上變形尾巴的頂點再重新上傳。這裡改成**只把鏈送過去** —— 9 個節點的偏轉角，
一個 `vec2[9]` uniform —— 由 vertex shader 依每個頂點烘焙好的「outerness」（尾根 0 → 尾梢 1）
自己內插。這個 outerness 藏在 normal 的第四個分量裡：三分量的 snorm16 attribute 本來就會被
驅動程式補齊到四個，所以讓尾巴變軟的那個通道，以 byte 計是免費的。

鏈的驅動來源是**世界朝向**，不是骨頭：這裡的轉身發生在 model matrix 上，
如果只看骨頭，過彎時尾巴會是死的 —— 而那正是真尾巴甩得最開的時候。

尾巴的**朝向**也改了。模型裡的弧線在 XY 平面，也就是往身體側面翹；
那在鎖定的四分之三視角下讀得出弧度，在自由視角下就只是一條往旁邊伸的尾巴。烘焙時繞 Y 轉四分之一圈，弧線就落到 YZ 平面，
從任何角度看都是往身後掃上去。這個旋轉烘進頂點而不是加到骨頭的靜止旋轉上 ——
它必須作用在姿勢**之後**，否則會把甩動軸一起帶走，尾巴就變成前後擺了。

### 鬍鬚：一個「把樞紐變成骨頭」的做法

鬍鬚和尾巴一樣在模型的可彎曲清單裡，但它們**繞臉頰上的一個樞紐彎**，不是繞自己骨頭的原點 ——
而 shader 只會繞骨頭原點轉。這正是它們一開始沒能跟尾巴一起做的原因。

解法是**給每根鬍鬚一根自己的骨頭，放在它的樞紐上**。沒有任何東西會擺動這 6 根骨頭，
它們純粹是為了「把原點放到對的位置」；放好之後，鬍鬚就跟尾巴共用同一套機制。

一根有樞紐的骨頭位於 `物件矩陣 · translate(樞紐)`，而這仍然是一個單純的 TRS ——
平移先被轉進物件自己的座標系而已。保持 TRS 形式，執行期就完全不需要為它們開特例。

驅動鏈也不同：鬍鬚跟**頭**，尾巴跟**身體**。所以貓只是轉頭而身體沒動時，鬍鬚會拖、尾巴不會。
臉的兩側在各自的局部座標系裡是**反號**的 —— 這樣它們在世界空間中才會往同一個方向拖。

每個頂點用哪條鏈，寫在骨頭那個 byte 裡：**低 5 bits 是骨頭索引，高 3 bits 是 sway group**。
沒有多花任何空間。（烘焙時會擋下超過 32 根骨頭的情況：無聲進位會變成一片三角形焊在錯的關節上。）

增益調高到 0.12（模型原值 0.05）：那個值適合「貓佔滿整個畫面」的近景，
這個場景是從更遠的地方看一隻更小的動物，0.05 在這裡的擺幅不到半度 —— 正確，但看不見。

### 骨架：沒有一個蒙皮權重

原模型是**剛體階層**動畫：每個部位是一整塊網格繞關節轉。所以不需要 glTF 意義上的骨架，
只需要 17 根骨頭的 TRS，和一次由父到子的前向遍歷。`bake-cat.mjs` 把骨頭之間所有靜態變換
**折進頂點裡**，執行期只剩 `applyPose` 真正會動的通道。

```
node tools/bake-cat.mjs                       # 三個花色，全部進同一個檔
node tools/bake-cat.mjs --skins orangin,tabby # 只要其中幾個
```

輸出 935 kB：position `f32`、normal `snorm16 × 4`（第四個分量是尾巴的 outerness）、
colour `sRGB u8` **每個花色一份**（骨頭索引就藏在第四個 byte 裡）、index `u16`。

三個花色**只有調色盤不同** —— 同一組頂點、同一組法線、同一份索引、同一副骨架 ——
所以幾何只存一次、調色盤存三份，比三隻完整的貓省下將近一 MB，
而且換花色是**一次 buffer 上傳**，不是重新載入。烘焙會斷言這件事，不是假設它：
某個花色若偷偷改了頭部細分，它的顏色就會套到別人的頂點上，貓會變成紮染。
**這是一次性的離線步驟，app 本身仍然零依賴、零建置**；three 只是隔壁專案的 devDependency，
永遠不會被 ship。

### 一個名字騙人的 bug

四條腿的相位曾經是錯的：貓像搖搖馬一樣，同一側的前後腳一起往前擺。

原因不在相位，在名字。上游模型的兩對腿是從**相反的兩端**命名的 ——
`hindHips[s < 0 ? 'R' : 'L']` 對上 `frontPaws[s < 0 ? 'L' : 'R']` —— 所以 `hipHL` 在
x = +0.92，而 `pawFL` 在 x = −0.35。相信名字，就會把每條後腿和**同側**的前腳配成一對。

現在配對是依**靜止位置的 x 符號**決定的，不看名字。唯一能可靠說出一條腿在哪一側的東西是它的
座標；就算上游哪天把名字改一致了，這裡也還是對的。`--interact` 裡有一項專門盯著它，
而且是取整個擺幅的極值來測 —— 每個步態一個週期會兩次經過零點，在那裡量什麼都會過。

### 光影：兩個方向

### 嘴部皺褶：修法線，不是修光

換成連續打光之後，口鼻周圍浮出一道生硬的弧線。那不是光照的錯，是**幾何的問題被照出來了**：
模型把口鼻平台從球面推出去，而推的範圍是一個硬邊界的條件式，沒有任何羽化 ——
曲面因此連續、但它的**導數不連續**，`computeVertexNormals()` 忠實地回報了那道折角。

三階 ramp 把折角兩側量化進同一階，所以看不見；連續打光看得見，而高光更是主動在替它宣傳。

修法是**平滑法線、不動頂點**。剪影、描邊殼、陰影代理全部不變 ——
只放鬆「每個點宣稱自己朝向哪裡」，而那正是原本錯的那個量。兩道都走索引緩衝：

- **weld**：同一個位置的頂點共用一條法線。球面幾何為了 UV 會在接縫與極點複製頂點，
  那些複製品原本各自帶著不同的法線，等於在後腦杓上另外開一條縫。
- **relax**：每個頂點取「與它共邊的頂點」的平均，保留自己一半的權重 ——
  這一步才是真正把折角軟化掉的。

只套用在**有手工切痕的兩個形狀**：頭（口鼻平台推出去的地方）和身體（底部被水平切平）。
兩者都用頂點色上色，這正好把它們和掛在同一根骨頭上的純色部位分開 —— 鼻子也在頭骨上。

**高光同時換成 sheen。** 毛皮不是拋光表面，不該有拋光表面的高光；它該有的是掠射角的絨光。
而且「寬」是重點：一個銳到能被讀成高光的 Blinn lobe，等於把內積取到約 28 次方 ——
那是個**誤差放大器**，會把相鄰法線之間的小小分歧變成一道可見的接縫。
sheen 是掠射項的低次方，面對同一組法線安靜得多。

沒有再加 wrap diffuse：做完上面兩件事之後明暗交界已經夠平滑，再軟化只會把立體感一起糊掉。

貓**不再用模型自帶的三階量化打光**，改用場景自己的那一套，逐項相同：
Lambert 漫射 × 主光 × 陰影、藍灰色環境光、Blinn-Phong 高光（指數由粗糙度導出）、
Fresnel 天空反射、距離霧。毛皮的參數是「很粗糙、非金屬」，所以高光是一片寬鬆的光澤而不是亮點。

模型自帶的 cel ramp 適合「貓就是整張畫面」的情境，平塗是那時的重點。
在這裡牠只是被同一顆太陽照到的其中一個物體，而只把牠的漫射量化，
會讓牠變成畫面上**唯一一個對光線反應不連續**的東西 —— 不管陰影做得多好，那都會讀成剪貼。

**黑邊留著。** 它們是墨線，不是明暗；打光停止「被畫出來」之後，正是它們維持住手繪感。
眼睛、鬍鬚、嘴也一樣保持平塗。

**陰影也是同一套。** 星團的整個分層距離場（含漣漪、質量消散、表面擾動）都從 march.js
搬進 `scenes/cluster.js`，兩邊呼叫**同一個** `clusterShadow()`、走同樣的分層、同樣的步數預算。
走比較簡單的場的陰影，等於是另一個略有不同的物體的陰影，而兩者**正好會在場景最活躍時分開**。

射線從開闊地面出發時幾乎立刻離開星團的包圍球，所以在野外成本就是一次 miss；
背對光的面根本不發射線。貓**不自我遮蔽** —— 牠的膠囊是粗略近似，有些地方會戳出真實表面之外，
拿它們自我遮蔽只會得到一片 acne。

**貓遮住地板。** 7 根膠囊掛在同一副骨架上，進到 shadow 與 AO 查詢裡。
它們在每個細節上都是錯的、在輪廓上是對的 —— 而陰影要的就只是輪廓。

**刻意不進主射線**：畫出畫面的射線仍然只看到星團，否則會有一隻糊糊的第二隻貓站在真的那隻裡面。
代理只服務「路上有沒有東西」這種問題，而那種問題分不出膠囊和貓。

### 一次值得記下的連結失敗

貓的陰影原本是用**行進**解的，結果 shader **連結失敗，而且 log 是空的**。

原因是 `softShadow` 會被編譯器內聯兩次（主射線一次、反射彈跳一次），多一個迴圈就撞上
D3D `ps_5_0` 的指令上限。空的 log 沒有給任何線索，所以是靠二分法找出來的：把膠囊數降到 2
仍然失敗，把那一行呼叫註解掉就過 —— 於是知道是「複雜度」而不是「數量」。

改成**解析解**之後就好了：軟陰影本來就是「射線最靠近遮蔽物的距離 ÷ 走到那裡的路程」，
而對一堆膠囊來說，那個最近距離有閉式解（射線對線段的最短距離）。完全沒有 t 迴圈，
每根膠囊只要幾個內積。而且這個答案**嚴格更好** —— 取樣式的行進可能一步跨過腿最細的地方。

星團用行進、貓用解析：同一個問題的兩種答案，各自對自己的形狀最便宜。

## 地面：三種造型

面板「地面」分組。**「網格」是預設，而且一行都沒有改** —— 它是這個場景的基準面，
說明地板在哪裡。另外兩種是 [src/scenes/ground.js](src/scenes/ground.js)：

| 造型 | 內容 |
|---|---|
| **網格**（預設） | 原本那片帶淡格線、會隨距離淡出的地板 |
| **純草地** | 立體草葉，隨風擺動 |
| **草地與花** | 加上隨機生成的花叢，叢的周圍散著落單的花 |

### 為什麼草不在距離場裡

地板是一個閉式解的平面，這是它幾乎不花錢的原因，也是它種不出東西的原因：
把十萬片草葉放進距離場，等於讓 sphere tracer 為了走到地面而經過每一片。

所以草根本不在場裡。它是**三角形**，畫進貓那張 target，用同一行深度比較去解 ——
就是上面那條交接。**沒有任何 mesh**：一片草是 7 個由 `gl_VertexID` 推出來的頂點，
一朵花是 48 個，沒有一個是載入來的。

草**連存都不存**，每幀從它那格的雜湊重新推導 —— 兩次 hash 攤在 7 個頂點上，比去記憶體
抓還便宜。花**存**，因為對花來說不是：見下面。

### 草皮跟著鏡頭走，草不跟

固定大小的草皮不是小到看得見邊，就是大到畫不動。所以格線**中心跟著鏡頭**（並往視線方向
推，把預算花在畫面裡而不是背後），而且**每一環各自對齊自己的格寬**；每一片草的位置、高度、
朝向都是從它那格的**世界座標**雜湊出來的。

格線在滑動，草沒有。種子若是跟著 instance 編號走，整片草原會隨著你走路而在地上爬行。
邊緣不是淡出也不是消失，是**縮回地裡** —— 唯一一種沒有東西可以彈跳的收邊。

`--interact` 有一項在守這件事：草皮原點永遠落在自己的格點上（偏差 `0.0e+0`）。

### 風是一個場，不是一段動畫

一個關於位置與時間的函數，草和花莖讀的是**同一份**。所以一陣風是以單一事件的形式
掃過整片地，而不是每株植物各自播放自己的擺動；花會跟著它周圍的草一起倒。

彎曲是**旋轉**，不是剪切：角度隨高度的平方成長（根部硬、接近尖端才給），每個點到根部的
距離不變。剪切過的草葉會愈倒愈長，而「整片草在風中一起變長」是把風做錯的最明顯徵狀。

### 第一版是一片焦黑的釘子

直立的草葉，法線是水平的。太陽在天上任何位置時，有一半的草原是背對它的 —— 於是全黑。
第一次算出來的畫面就是一整片燒焦的鐵釘。

眼睛不會把草坪讀成一百萬片直立的平面，它讀成一個**表面**，而那個表面朝上。
所以法線往正上方偏（`SWARD_BIAS`），草叢的形狀就退回成那個表面上的變化，而不是全部的訊號。
另外草只有一個細胞厚，背光時會透 —— 那道透光是「草原」和「一堆綠刺」之間的大半差別。

同一個道理讓草底下的土是**綠的而不是棕的**：沒有任何 instance 預算能讓每平方公分都站一片草，
所以縫隙露出來的東西必須跟站在裡面的東西同色 —— 是俯視的深色草皮，不是底下的泥。
棕色的地會讓稀疏的草變成犁過的田上的殘株。

### 花是按叢種的

一個 4 公尺的粗格，每格擲一次骰決定長不長；叢裡的花往中心堆，並**往邊緣愈來愈稀** ——
出來的是「密的中心加上周圍幾株落單的」，而不是一塊有邊界的花圃。一叢是一個品種，
所以顏色是按叢雜湊的。

花的作用半徑比草**短**（0.62 倍）：一片遠處的草還有意義，因為它貢獻的是遠景的**顏色**；
那個距離的一朵花不到一個 pixel。

花莖被刻意做得比草高一截。頭跟草齊高的花是永遠不會被看到的花 —— 除了正上方，
草皮從每個角度都會蓋過它。

### 花只算一次（一個真 bug）

第一版把上面那整串 —— 這格長不長、叢心在哪、叢多寬、這朵有沒有被稀掉 —— 寫在
vertex shader 裡。它有兩個問題，一個是浪費，一個是錯的。

**錯的那個**：花的格子是 4 公尺一格，但整個草皮的原點只對齊 **0.5 公尺**的草格線。
於是相機每走半公尺，花格的角點就換一個位置，整叢花被重新擲一次骰 ——
**花的位置一直在變**。草是對的（它的格線就是那 0.5），花不是。

**浪費的那個**：一朵花有 48 個頂點，每一個都要把那整串算完，得到同一個答案；
而那個答案每一幀也都一樣。

現在改成**在 CPU 上播種**，只在草皮原點移動整整一個花格時才重算 —— 走直線大概每幾公尺
一次，站著不動則永遠不會。結果丟進一個 instance buffer，vertex shader 只讀。
被稀掉的花根本不會進 buffer（以前是進去了才在 shader 裡丟掉，白跑一趟 vertex shader）。

播種用的雜湊是**世界格座標的函數**，跟草的道理一樣 —— 所以重播之後，兩份 buffer 共有的花
會落在**完全相同**的座標上。`--interact` 有三項在守這件事：站著不動不重播、
拖曳整段鏡頭只重播一次、而且 257 朵裡有 206 朵位置一致到 0.1 mm。

唯一不能預先算的是**邊緣淡出**：那是從眼睛「現在」的位置量的，而眼睛是連續移動的。
那留在 shader 裡，一個 `length()` 加一個 `smoothstep`。

### 視距：加的是面積，不是尺寸

「一望無際的草原」和「把幀數還我」是同一個滑桿的兩端（8–120 單位）。

第一版是**一個格線、格寬隨視距開根號變大**。成本確實壓下來了，而且完全錯：
放大格寬等於放大整個圖樣，所以視距一拉遠，**腳邊的草就變稀**。
要的是更多草地，拿到的是同一片草地被放大。

所以近處的格寬**永遠不變**。距離是靠往外加**環**買來的 —— 一圈圈同心方形帶，
每一圈比裡面那圈粗，中間挖掉裡圈已經蓋過的部分。**第 0 環在任何設定下都是同一片草坪。**

環的粗細比不是寫死的 2，是解出來的：`step = (視距 / 16)^(1/(環數-1))`，
好讓最外圈**正好**落在要求的視距上，而不是跳到下一個 2 的冪 —— 滑桿因此是連續的。
挖洞時往內縮一格，讓環之間**寧可重疊也不要留縫**：兩圈各自對齊自己的格寬、邊界不會對齊，
重疊一條帶子看不出來，留一圈裸土則是災難。

成本隨**環數**成長，也就是視距的對數：

```
8 單位   → 1 環 / 16,384 片草
120 單位 → 5 環 / 81,920 片草      15 倍視距，5 倍的草
```

而且 8 單位和 120 單位用的是**同一個 0.5 格寬**。`--interact` 兩項在守這件事。

實測 120 單位是 20.2 ms —— 跟舊版 44 單位一樣的成本，多看了將近三倍遠。

花的叢格同理固定在 4 公尺，改成**限制它能走多遠**（34 單位封頂）：
遠處的草還貢獻顏色，遠處的花頭連一個 pixel 都不到。

### fragment shader 幾乎是空的

草在畫面下半部疊了好幾層深，所以 fragment shader 裡的任何東西都要為了一個幾 pixel 高的
東西付好幾次。光照和霧都改在**逐頂點**解決（霧裡那個 220 次方尤其貴），
fragment 只剩一件事：把花心的方形四角丟掉，讓它在畫面上是圓的。

WebGL2 + `EXT_color_buffer_float`。時間累積存在浮點貼圖裡，沒有浮點 render target 無法運作 ——

python -m http.server

## 驗收工具：`tools/verify.mjs`

同樣零依賴。它用 Node 內建的 `WebSocket` 與 `fetch` 直接講 Chrome DevTools Protocol ——
沒有 puppeteer、沒有 playwright、沒有測試框架。協定就是 socket 上的 JSON，這就是全部的依賴表面。

```bash
node tools/verify.mjs                # 六種設定各載入、渲染、截圖，回報任何 console error
node tools/verify.mjs --interact     # 端對端互動驗收（真的去拖曳滑鼠、滾滾輪、按鍵）
node tools/verify.mjs --responsive   # 手機 / 平板 / 筆電 / 超寬視窗版面與像素預算
node tools/verify.mjs --bench        # 固定負載的效能量測，逐項拆解成本
node tools/verify.mjs --bench --gpu high   # 同上，但強制用獨顯
node tools/verify.mjs --diff         # 凍結時間、翻轉設定、逐像素量出「看不看得出來」
node tools/verify.mjs --head         # 開可見的瀏覽器視窗
node tools/verify.mjs --serve        # 只開靜態伺服器
node tools/verify.mjs --eval probe.js --at "#/march"   # 在頁面裡執行探針，檢查活的 GPU 狀態
```

截圖輸出在 `tools/shots/`。除了抓圖之外它還會斷言：畫布不是單一顏色（全黑代表沒渲染）、
`gl.getError()` 乾淨、沒有未捕捉的例外。

`--interact` 的 23 項檢查涵蓋：intro 關閉、**點擊真的擊中表面**、**留下漣漪**、
**漣漪被宿主帶著移動**、**點在天空不會有反應**（CPU 的挑選與螢幕上看到的一致）、
指標事件真的進到畫布、拖曳繞行鏡頭、滾輪縮放、XY 盤轉動光源、`Ctrl`+`K` 面板、模糊搜尋、
**主品質滑桿一次推動七項**、**個別滑桿仍能覆蓋主滑桿**、
渲染縮放真的重配了 render target、參數往返 URL、暫停真的停住時鐘、`.` 前進一幀、
禪模式、快捷鍵表、單場景時隱藏 tab bar、恢復預設值，以及全程零 console error。

每次執行前還會先跑一個一毫秒的 lint：掃描所有著色器樣板字串裡有沒有反引號。
GLSL 註解裡的一個反引號會提前結束 JS 樣板字串，然後在五十行之外炸成一個
毫不相干的識別字錯誤 —— 這件事我踩了三次才決定寫成檢查。

合成點擊不用眼睛瞄「畫面中間」，而是把球心投影成 CSS 座標再點下去 ——
用眼睛瞄的話夠常落在空無一物的天空，足以讓測試對它宣稱在檢查的功能說謊。

### 它抓到的八個真 bug

1. **`[hidden]` 被 CSS 打敗。** `.fallback { display: grid }` 的優先權高於 UA 對 `[hidden]` 的
   `display: none`，所以「需要 WebGL2」的錯誤畫面一直蓋在正常運作的網站上面。
2. **切換場景時 render target 停在 2×2。** 換場景不會改變畫布尺寸，所以 `_resize()` 的
   「有變化嗎？」提早 return，新場景永遠拿不到真正的解析度。
3. **`gl_PointSize < 1` 的粒子被硬體丟棄。** `ALIASED_POINT_SIZE_RANGE` 在這張 GPU 上從 1 開始，
   而透視除法把點的大小算到 0.29 —— 26 萬個粒子一個都沒畫出來。
4. **拖曳在開始的那一幀就被取消。** 用 `setPointerCapture` 之後又監聽 `pointerleave` 來結束拖曳
   是錯的：呼叫 capture 本身就會觸發一組 out/leave。
5. **場景上下顛倒。** `right` 算成了 `cross(worldUp, fwd)` 而不是 `cross(fwd, worldUp)`，
   負號穿過下一個外積傳給 `up` —— 格線地板一直畫在天空裡，而場景夠對稱，
   對稱到這件事看起來像是刻意的構圖。
6. **View Transition 被中斷時丟出未處理的 rejection。**
7. **靜態的 hint 區塊被當成有值的控制項註冊。** 它帶了 `id`，於是進了 state map，
   第一次程式化 `setValues()` 打到一個沒有 `set()` 的元素就爆掉。
8. **低幀率時點擊沒有反應。** 靠算繪迴圈取樣 `pointer.down` 來判斷點擊是錯的，
   25 fps 下一次快速點擊可以整個發生在兩幀之間 —— 要在 pointer 事件上判定。
   （這個修正留在 `core/pointer.js` 的 `onDown` / `onUp` 回呼裡，目前沒有人用。）

第 5 個特別值得一提：它是被截圖裡「格線出現在地平線上方」這個細節抓到的，
而不是被任何斷言抓到的 —— 這正是為什麼驗收工具要輸出可以用眼睛看的東西。

## 效能

`--bench` 跑固定負載（關掉鏡頭自轉與時間累積，兩者都會把成本藏進被抹掉的幀裡），
量最近 90 幀的中位數與 p95，再逐項拆解每個著色項的成本。
**讀 GPU ms 而不是 fps** —— 著色器一旦夠快，幀時間就會貼在合成器的節奏上，
每個案例都讀到同一個數字，那什麼也沒告訴你。

1600×900，全解析度的 GPU 時間：

| | Iris Xe | GTX 1650 |
|---|---|---|
| 優化前 | 42.5 ms | 22.9 ms |
| **優化後** | **9.0 ms** | **4.6 ms** |

程式端 4.7 倍、換獨顯 2 倍，合起來 **42.5 → 4.6 ms，約 9 倍**。畫面是同一張。

### 程式端做了什麼

**地板不再被 march。** 平面就用 `t = (FLOOR_Y − ro.y) / rd.y` 一步算完，
再和星團的結果比誰近。掠射射線本來會沿著地板把整個步數預算走完，什麼也沒換到。
（附帶修掉一個 bug：舊版地板會被步數預算截斷，所以格線的消失距離會隨「行進步數」滑桿改變。）

**星團有一個包圍球**，每幀在 JS 用擺放球體的同一組數字算出來（再加上 smin 的外凸、
擾動振幅、進行中的漣漪振幅）。著色器需要的每一個距離都從它推導：從哪裡開始 march、
何時放棄、陰影射線走到多遠還有意義。**著色器裡一個寫死的尺度都不剩**，
所以之後改場景大小不用重調六個常數。

包圍球還讓 march 從**進入點**開始，而不是從鏡頭前面慢慢逼近；沒打到包圍球的射線直接跳過。

**噪聲只在接近表面時算。** `snoise` 是整個著色器裡最貴的函數，原本每像素被呼叫約 264 次
（主射線、法線、陰影、AO，反射再一輪）—— 包括那些離表面還很遠、位移根本不可能影響結果的
取樣點。超出一個幾倍振幅寬的帶狀區時改回傳 `d − 振幅`，那是真實距離的合法下界，
追蹤器保持保守、不會穿透，而且完全跳過噪聲。

**場的三層。** `clusterBase`（球+環）→ `clusterShape`（+漣漪）→ `clusterFull`（+噪聲）。
陰影與 AO 用哪一層是個開關，因為那是判斷不是事實 —— 見下面的量測。

**背光面不打陰影射線。** `ndl <= 0` 時結果會被乘上 0，原本照樣跑 48 次場求值。

**距離場沒被擾動時，步長從 0.88 放回 0.97。** 0.88 是為了噪聲與漣漪才壓的。

### 品質旋鈕

七個旋鈕（渲染縮放、行進步數、陰影步數、遮蔽取樣、反射步數、陰影含表面擾動、
反射含陰影遮蔽），外加一個**總體品質**主滑桿：碰它就一次寫入全部七項。
主滑桿是一個**動作而不是綁定** —— 之後你仍可單獨微調任何一項，主滑桿只是變成過時的讀數。

`--diff` 凍結模擬時間、翻轉一個設定、重繪、逐像素比較，所以「這個看不出來」是量出來的
而不是講出來的。實測拐點（最大通道差歸零的位置）：

| 預算 | 拐點 | 預設 |
|---|---|---|
| 行進步數 | ~70 | 100 |
| 陰影步數 | 32 | 32 |
| 遮蔽取樣 | 5 | 5 |

品質曲線的中點就落在這些拐點上：往上是買鏡頭角度與參數組合的餘裕，往下才開始換掉看得見的東西。

兩個開關則**確實看得出差別**，只是範圍極小：關掉「陰影含表面擾動」有 0.16% 的像素
差超過 2 階、最大差 85；「反射含陰影遮蔽」是 0.19% 與最大 103。
兩者現在各只要約 1 ms，所以預設都開著 —— 預設畫面等同優化前，改變的是速度不是圖。

---

**Chrome 預設不會用獨顯。** WebGL context 上的 `powerPreference: 'high-performance'`
是頁面在瀏覽器**已經決定用哪張卡之後**才給的提示，它自己搬不動你。要真的切過去：

- **Windows 設定 → 系統 → 顯示器 → 圖形** → 加入 `chrome.exe` → 高效能，或
- **NVIDIA 控制面板 → 管理 3D 設定 → 程式設定** → Chrome → 高效能 NVIDIA 處理器

設好之後跑 `node tools/verify.mjs --bench`（**不加** `--gpu`），
它印出的 renderer 字串會直接告訴你成功了沒 —— 那個設定是綁執行檔路徑的，
所以驗收工具用的臨時 profile 也吃得到。
